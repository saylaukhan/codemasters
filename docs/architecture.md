# Архитектура

Файл заполняется, когда появится код — после этапа 1 плана (`docs/product/plan.md` §14), то есть когда пройдёт
сквозной путь замера от агента до БД (T-01, T-02, T-05, T-06–T-11, T-14–T-18). До этого
описывать нечего: всё, что могло бы быть здесь, — план, а не факт.

Что здесь будет: как устроено приложение по частям (`agent/`, `backend/`, `web/`), где проходит
граница сервера и клиента, как ходят данные — агент → API → БД → Celery → уведомления;
панель → API.

Пока — ссылки на источники. Схема системы и состав Docker Compose — plan.md §3; клиентский
агент — plan.md §4; схема БД — plan.md §5; логика статусов — plan.md §6; инциденты и
уведомления — plan.md §7; роли и доступ — plan.md §9; API — plan.md §10. Принятые решения:
ADR-002 (стек), ADR-003 (модель данных), ADR-008 (роли и область видимости), ADR-009 (формат
ошибок и ответов API) — `docs/architecture/decisions/`.

Вопросы, на которые файл должен ответить, когда будет написан:

1. Какие процессы работают в проде (`caddy`, `api`, `worker`, `beat`, `db`, `redis`, `web`, `speedtest`) и за что отвечает каждый.
2. Что происходит с замером от записи в SQLite-очередь агента до строки в `measurements` и статуса школы на карте.
3. Где считается статус замера и школы, откуда берутся пороги и куда пишется их снимок (ADR-004).
4. Как устройство доказывает принадлежность своей школе и почему School ID не берётся из запроса (ADR-005).
5. Как запрос панели проходит проверку прав: JWT → `require(permission)` → RLS по `app.user_scope` (ADR-008).
6. Что Celery делает после каждого замера и по расписанию, и как уведомление попадает в `notification_log` (ADR-007).
7. Как OpenAPI-контракт связывает backend и панель и когда перегенерируется клиент `web/src/api/generated/*` (ADR-009).
