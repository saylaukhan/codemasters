# Нагрузочный тест и индексы (T-56)

Как прогнать нагрузку на данных симулятора, какие цифры считать приемлемыми, что делать,
если медленно, и по каким EXPLAIN принимается решение о новом индексе.

Задача — T-56 в `docs/tasks/README.md`; этап 6 плана («нагрузочный тест, симулятор 1000
агентов», `docs/product/plan.md` §14). Эндпоинты, которые меряем, названы в задаче:
`GET /api/map/schools`, `GET /api/dashboard/summary`, `GET /api/analytics`,
`POST /api/measurements/batch`.

## 2. Как прогнать

Нагрузку меряют на **локальной** базе разработки. Не на боевой: сценарий заводит свои
устройства на настоящих точках мониторинга и шлёт от них замеры.

```bash
cp .env.example .env                     # если файла ещё нет
make backend-install                     # backend/.venv с зависимостями
make up                                  # db, redis, speedtest, ndt7
make migrate && make seed                # схема, справочники, dev-пользователи
```

Симулятор наливает данные **через API** — прямой записи в БД у него нет (`simulator/README.md`),
поэтому сервер должен быть поднят, а пароль администратора передан явно:

```bash
make api                                 # отдельный терминал, http://localhost:8000
SIM_ADMIN_PASSWORD='<пароль admin@example.kz>'  make simulate n=1000 days=90
```

Пароль dev-пользователей — в `AGENTS.md` §7. Без `SIM_ADMIN_PASSWORD` симулятор завершится с
кодом 2 и сообщением «Нужен пароль администратора». Две вещи из `simulator/README.md`,
«Ограничения», на которые надо закладываться заранее: `--days 90` принимается, но история
честно обрезается до 30 суток (сервер не берёт замер старше `MAX_QUEUE_AGE`), а регистрация
1000 ПК упирается в `AGENT_REGISTER_RATE_LIMIT` и занимает около часа. То есть глубина данных
под нагрузкой — месяц, и это пишется в журнал вместе с цифрами.

Сам прогон — с остановленным `make api` (иначе два процесса делят пул базы):

```bash
cd backend
export VKO_LOAD_DATABASE_URL='postgresql+asyncpg://vko:vko@localhost:5432/vko_monitor'
.venv/bin/pytest tests/test_load_endpoints.py -s
```

DSN — тот же, что `DATABASE_URL` в `.env` (имя базы по умолчанию — `vko_monitor`,
`.env.example`), обязательно с драйвером `+asyncpg`. `-s` нужен: таблица печатается в stdout,
без него pytest её проглотит.

Что можно подкрутить переменными окружения:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `VKO_LOAD_DATABASE_URL` | — | база с данными; без неё тесты пропускаются |
| `VKO_LOAD_REPEATS` | 20 | вызовов на эндпоинт в последовательной фазе |
| `VKO_LOAD_DEVICES` | 1000 | агентов, шлющих батч одновременно |
| `VKO_LOAD_BATCH_ITEMS` | 10 | записей в батче (контракт разрешает 100) |
| `VKO_LOAD_POOL` | 5 | соединений в пуле |
| `VKO_LOAD_OVERFLOW` | 10 | соединений сверх пула |
| `VKO_LOAD_STRICT` | пусто | любое значение превращает бюджеты §3 в ассерты |

Прогнать только одну фазу: `-k latency` или `-k concurrent`.

`VKO_LOAD_REPEATS` выше ~100 поднимать нельзя: последовательная фаза шлёт все вызовы батча с
одного устройства, а лимит T-51 — 120 запросов за 60 с на устройство, и фаза начнёт мерить
лимитер.

### Что в сценарии настоящее, а что нет

Значения пула по умолчанию — 5 + 10 — это дефолт SQLAlchemy, то есть ровно то, на чём живёт
боевой API: `backend/app/core/db.py` создаёт движок без `pool_size` и без `max_overflow`.
Если поменяли — это эксперимент про пул, и значения идут в журнал рядом с цифрами. Один
отход сделан сознательно: `pool_timeout` поднят с 30 до 300 с, потому что во второй фазе
тысяча запросов стоит в очереди за соединениями намеренно.

- **Лимит частоты T-51 — включён.** Он считается по устройству (`rl:device:<id>`,
  `backend/app/core/ratelimit.py`), поэтому 1000 разных устройств по одному батчу его не
  достигают, а обращение к Redis остаётся в измеряемом пути — боевой агент платит его всегда.
  Redis должен быть поднят; если счётчик не отвечает, middleware пропускает запрос с
  предупреждением в логе, и такой прогон в журнал писать нельзя.
- **Постановка в Celery (`enqueue_detection`) — отключена** autouse-фикстурой
  `detection_queue` из `conftest.py`; воркер для нагрузки не нужен.
- **Аудит в измеренные времена не входит,** и это не отключение: ни один из четырёх
  эндпоинтов не пишет строку в `audit_log`. Три GET отсекаются по методу
  (`CHANGING_METHODS`), а принятый батч агента аудит пропускает сознательно —
  `backend/app/auth/audit.py`. `audit_sessions` в сценарии подменён только затем, чтобы
  отклонённый запрос писался в ту же базу, что меряем.
- **Настоящие:** RLS роли `vko_panel` (ADR-008) и проверка токена устройства argon2id
  (ADR-005) — вторая делается прямо в event loop, см. §4, шаг 1.

### Если прогон оборвался

Уборка живёт в `finally` контекстного менеджера: Ctrl-C, таймаут или убитый интерпретатор её
не выполнят, и на настоящих школах останутся устройства `load-…` с замерами — они попадут в
расчёт статуса школы (ADR-004, T-16). Убрать вручную:

```bash
docker compose exec db psql -U vko -d vko_monitor
```

```sql
BEGIN;
DELETE FROM measurements m USING devices d
 WHERE d.id = m.device_id AND d.device_uid LIKE 'load-%';
DELETE FROM heartbeats h USING devices d
 WHERE d.id = h.device_id AND d.device_uid LIKE 'load-%';
DELETE FROM outages o USING devices d
 WHERE d.id = o.device_id AND d.device_uid LIKE 'load-%';
DELETE FROM devices WHERE device_uid LIKE 'load-%';
COMMIT;
```

## 3. Что считать приемлемым

Чисел отклика в ТЗ нет — ни одного. Значения ниже это **предложение**, рабочая цель этапа 6,
и лид их подтверждает или меняет, прежде чем на них где-нибудь сошлются как на критерий.
Они же зашиты в `BUDGET_MS` сценария.

| Эндпоинт | p95, мс | Откуда цифра |
|---|---|---|
| `GET /api/map/schools` | 2000 | карта рисуется один раз при входе, 350 маркеров |
| `GET /api/dashboard/summary` | 1500 | главный экран, открывается первым |
| `GET /api/analytics` (месяц, район) | 3000 | самый тяжёлый отчёт, открывается осознанно |
| `POST /api/measurements/batch` | 300 | 1000 ПК × 5 замеров в сутки — нагрузка редкая |

Бюджет батча сравнивается с полным временем ответа, в которое входит проверка токена argon2
(§4, шаг 1). Если она одна съедает бюджет — это вывод про процессор, а не про базу, и
сравнивать с 300 мс уже нечего.

Вторая фаза оценивается не временем, а результатом: **1000 батчей — 0 отказов, 0 потерь**.
Это требование «Сделано, когда» T-56 и инвариант ADR-006. Время приёма пишем в журнал
справочно.

Шаблон для `docs/worklog.md` — вставить и заполнить обе таблицы:

```text
Нагрузка T-56, <дата>, <данные: N школ / M ПК / K суток>, пул <POOL>+<OVERFLOW>:

| Эндпоинт                             | p50 | p95 | max | SQL | Вердикт |
|--------------------------------------|-----|-----|-----|-----|---------|
| GET /api/map/schools                 |     |     |     |     |         |
| GET /api/dashboard/summary           |     |     |     |     |         |
| GET /api/analytics (month, district) |     |     |     |     |         |
| POST /api/measurements/batch         |     |     |     |     |         |

Проверка токена argon2: <N> мс на запрос агента.
1000 батчей по 10 записей: <время> с, отказов <N>, потерь <N>.
Индексы: <добавлены такие-то новой миграцией | не добавлены, все запросы уложились>.
После индексов (если добавлялись) — вторая такая же таблица.
```

«До и после» из «Сделано, когда» — это два прогона одной и той же командой: первый до
миграции с индексами, второй после `make migrate`. Обе таблицы идут в журнал.

## 4. Что делать, если медленно

По шагам, снизу вверх — сначала понять, потом индексировать:

1. **Проверить, не упёрлись ли в процессор.** Сценарий печатает «Проверка токена argon2: N мс».
   `current_device` (`backend/app/core/deps.py`) зовёт `verify_secret` синхронно в event loop, а
   `backend/Dockerfile` запускает один воркер uvicorn — значит эти миллисекунды складываются
   последовательно. Если `N × 1000` сопоставимо со временем второй фазы, узкое место — argon2,
   и ни один индекс его не уберёт: это отдельная задача (вынести проверку в пул потоков либо
   удешевить параметры `PasswordHasher`), решение за лидом.
2. **Посмотреть на колонку `SQL`.** Абсолютного «правильного» числа у неё нет — первый прогон
   и есть базовая линия, её записывают в журнал. Признак «запрос в цикле» — не величина, а
   рост: число команд на один ответ не должно зависеть ни от количества школ, ни от глубины
   истории. Проверяется двумя прогонами — на `make simulate n=100 days=30` и на
   `n=1000 days=90`; если число выросло, это чинится кодом, а не индексом.
3. **Снять EXPLAIN из §6** для запроса за медленным эндпоинтом.
4. **Сверить с кандидатами §5.** У каждого написано, что в плане его подтверждает и что
   опровергает. Индекс добавляется, только если план подтвердил.
5. **Новая миграция** — forward-only, `YYYYMMDD_HHMM_short_name`, `down_revision` на текущий
   head (ADR-003). Старые миграции не трогаем. Индекс, который добавили миграцией, тем же
   слиянием прописывается в `__table_args__` модели, иначе следующий `make migration` его
   снесёт (так сделано в `20260917_0006_schema_v1.py`, комментарий у строки 445).
6. **Прогнать §2 второй раз** и положить обе таблицы в журнал.

Чего делать **не** надо:

- Удалять «дублирующие» индексы: тест `test_every_foreign_key_has_an_index`
  (`backend/tests/test_schema.py`) требует, чтобы каждый внешний ключ был покрыт индексом,
  начинающимся ровно с его колонок. Снятие индекса без замены роняет его.
- Вешать индекс на `m_hourly` / `m_daily` по имени представления — см. K5.
- Строить индекс на гипертаблице на боевой базе без `CREATE INDEX CONCURRENTLY`: TimescaleDB
  раскатывает его по всем чанкам и блокирует запись. В alembic это требует
  `op.get_context().autocommit_block()`.

## 5. Кандидаты в индексы

Разбор по коду. Колонка «Вердикт» — результат чтения схемы и запросов, **не** результат
замера; решает EXPLAIN из §6.

Что уже есть (`20260917_0006_schema_v1.py`, `20260918_0120_status_and_availability.py`):

- `measurements` (гипертаблица по `measured_at`): PK `(id, measured_at)`,
  `uq_measurements_measurement_uuid (measurement_uuid, measured_at)`,
  `ix_measurements_measured_at`, `ix_measurements_device_id_measured_at`,
  `ix_measurements_line_id_measured_at`.
- `heartbeats` (гипертаблица по `ts`): только PK `(device_id, ts)`.
- `outages`: PK, `uq_outages_device_id_started_at`, `ix_outages_line_id_started_at`.
- `schools`, `lines`, `devices`, `monitoring_points`: PK, уникальные ключи и индексы на все
  внешние ключи — их наличие стережёт `test_every_foreign_key_has_an_index`.

| # | Кандидат | Вердикт |
|---|---|---|
| K1 | `measurements (line_id, measured_at DESC)` + `INCLUDE` статуса и типа | решает EXPLAIN A |
| K2 | `measurements (device_id, measured_at DESC)` + `INCLUDE` статуса | решает EXPLAIN B |
| K3 | `heartbeats (ts)` или частичный `(device_id, ts) WHERE online` | **не нужен** |
| K4 | `lines (status, school_id)`, `schools (is_active)`, `schools (full_name)` | **не нужен** |
| K5 | индексы на `m_hourly` / `m_daily` | **сначала снять EXPLAIN E** |
| K6 | дедупликация батча в `store_measurements` | **не индекс — вопрос лиду** |

**K1.** `ix_measurements_line_id_measured_at` ведёт по `(line_id, measured_at)` — это ровно
то, что нужно порядку `ORDER BY measured_at DESC LIMIT 3` в LATERAL «последние N замеров
линии» (`backend/app/services/status.py`, и `last` карты в `services/overview.py`). Но в
индексе нет ни `quality_status`, ни `iface_type`, а в `WHERE` они есть: каждая
строка-кандидат читается из кучи, и только там выясняется, что она Wi-Fi или без статуса.
*Подтверждает:* в плане A `Rows Removed by Filter` заметно больше нуля. *Опровергает:* около
нуля — тогда доля Wi-Fi мала и покрывающий индекс только утяжелит запись в самую горячую
таблицу. Риск: `INCLUDE` на гипертаблице надо проверить на той версии TimescaleDB, что стоит,
и раскатка по всем чанкам на непустой базе долгая. Запасной вариант, если доля Wi-Fi велика, —
частичный индекс `WHERE iface_type IS DISTINCT FROM 'wifi'`, но это двойная цена вставки.

**K2.** То же рассуждение для `ix_measurements_device_id_measured_at` и `DISTINCT ON
(device_id)` в `problem_devices` (`backend/app/services/overview.py`). Слабее K1: здесь у
периода есть обе границы, поэтому чанки отсекаются и читать приходится меньше.

**K3.** PK `heartbeats` — это уже `(device_id, ts)`, точное совпадение и для коррелированного
`max(ts)` из `school_statuses`, и для `EXISTS` из сводки. `ts` — колонка партиционирования,
так что `ts > :start AND ts <= :end` отсекает чанки и без отдельного индекса, а внутри
оставшихся расчёт доступности (`backend/app/services/availability.py`) читает почти все
строки двумя оконными функциями — на такой выборке seq scan выигрывает у индекса.
Единственный добавочный фильтр `online` истинен почти везде, поэтому частичный индекс по тем
же колонкам — это почти вся таблица второй раз.

**K4.** 350 школ, ~700 линий, 1000 устройств, ~20 районов. На таких таблицах планировщик
выберет seq scan и индекс не тронет, зато платить за него при каждой записи придётся. То же
про `ORDER BY schools.full_name`: сортировка сотен строк идёт в памяти.

**K5.** `m_hourly` и `m_daily` — continuous aggregates. В миграциях
`20260918_0300_measurement_aggregates.py` и `20260918_0330_aggregates_below_contract.py` нет
ни одного явного `CREATE INDEX`, но `timescaledb.create_group_indexes` там не выключен, значит
TimescaleDB сам завёл групповые индексы по колонкам `GROUP BY`. Какие именно — в репозитории
не зафиксировано, снимать надо на живой базе (§6, блок E). Пока список не снят, любой индекс
на агрегате — гадание. И вешать его надо не на имя представления, а на материализующую
гипертаблицу `_timescaledb_internal._materialized_hypertable_N`, номер которой в каждой
установке свой; миграция с зашитым номером сломается на другой базе. Правильный путь — взять
имя из `timescaledb_information.continuous_aggregates` и подставить в `op.execute`.

**K6.** Ведущая колонка `uq_measurements_measurement_uuid` — уже `measurement_uuid`, так что
дело не в нехватке индекса. Не хватает границы по `measured_at`: без неё TimescaleDB не может
отсечь чанки и опрашивает локальную копию индекса в каждом (90 суток — порядка 13 недельных
чанков на запрос, см. EXPLAIN D). Новый индекс числа чанков не изменит. Лечится кодом —
добавить в `store_measurements` нижнюю границу `measured_at >= now() - MAX_QUEUE_AGE` (окно
очереди агента, 31 сутки, `backend/app/schemas/agent.py`). Это правка
`backend/app/api/agent.py` и касается идемпотентности ADR-006, то есть **не файл T-56**:
решение за лидом, отдельной задачей.

### Миграция в этом слиянии не создана

Сознательно. Ни один кандидат не проходит порог «отсутствие очевидно из схемы и запроса»:
K3, K4 и K6 закрыты существующими индексами или отброшены размером таблицы, K1 и K2 зависят
от чисел, которые даёт только EXPLAIN на настоящих данных, K5 нельзя написать, не посмотрев
на живую базу. Проверить миграцию в той сессии, где писался этот документ, было нечем — ни
Docker, ни `backend/.venv`, — а сломанная миграция роняет CI и чинится только новой ревизией
(forward-only, ADR-003). Порядок такой: сначала §2 и §6, потом решение по K1, K2 и K5, потом
миграция — по шагу 5 из §4.

## 6. EXPLAIN под решение

Запускать в `psql` на той же базе, где гнали нагрузку:

```bash
docker compose exec db psql -U vko -d vko_monitor
```

Запросы панели ходят под ролью `vko_panel` с областью видимости (ADR-008), а приложение
владеет таблицами и RLS на него не действует. Чтобы план совпал с боевым, оборачиваем блоки
A и B в транзакцию с ролью. `all` — область администратора и области «Область»:

```sql
BEGIN;
SET LOCAL ROLE vko_panel;
SELECT set_config('app.user_scope', 'all', true);
-- сюда EXPLAIN из блока A или B
ROLLBACK;
```

Блоки D и E — под владельцем, без роли: агент и служебные запросы ходят именно так.

Буквы блоков — по эндпоинтам: A — карта, B — сводка, C — аналитика, D — батч, E — агрегаты.
Здесь только те четыре плана, которые решают судьбу живых кандидатов; блока C нет — у
аналитики кандидатов не осталось. Планы остальных запросов (основной SELECT карты, средние
сводки, доступность по heartbeats) снимаются тем же способом из соответствующих сервисов —
они понадобятся, только если §4 укажет на них.

### A. Последние N замеров основных линий — подтверждает или опровергает **K1**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT l.school_id, latest.measured_at, latest.quality_status
  FROM lines l
  JOIN LATERAL (
       SELECT m.measured_at, m.quality_status
         FROM measurements m
        WHERE m.line_id = l.id
          AND m.measured_at <= now()
          AND m.iface_type IS DISTINCT FROM 'wifi'
          AND m.quality_status IS NOT NULL
        ORDER BY m.measured_at DESC
        LIMIT 3) latest ON true
 WHERE l.status = 'main'
   AND l.school_id IN (SELECT id FROM schools WHERE is_active);
```

Смотрим: `Rows Removed by Filter` во внутреннем узле. Около нуля — K1 не нужен. Десятки и
больше на каждую линию — K1 обоснован. Заодно видно, как далеко назад уходит индексный скан
для линии без замеров: у карты нет нижней границы периода.

### B. Проблемные устройства сводки — подтверждает или опровергает **K2**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM (
  SELECT DISTINCT ON (m.device_id) m.device_id, m.quality_status
    FROM measurements m
    JOIN lines l ON l.id = m.line_id
   WHERE l.school_id IN (SELECT id FROM schools WHERE is_active)
     AND l.status = 'main'
     AND m.iface_type IS DISTINCT FROM 'wifi'
     AND m.measured_at >= now() - interval '24 hours'
     AND m.measured_at < now()
   ORDER BY m.device_id, m.measured_at DESC) last
 WHERE last.quality_status IN ('unstable', 'critical', 'offline');
```

Период сводки по умолчанию — сутки, подставлен явно. Смотрим то же, что в A, плюс сколько
чанков осталось после отсечения: за сутки должен остаться один-два.

### D. Дедупликация батча — цена вопроса **K6**

Приложение шлёт готовый список из 100 значений, а подзапрос планировщик свернёт в semi-join и
план получится не тот. Поэтому сначала достаём список, потом подставляем его буквально:

```sql
-- шаг 1: собрать 100 настоящих uuid одной строкой
SELECT string_agg(quote_literal(measurement_uuid::text), ', ')
  FROM (SELECT measurement_uuid FROM measurements ORDER BY measured_at DESC LIMIT 100) s;

-- шаг 2: подставить вывод шага 1 вместо <СПИСОК> — так запрос и уходит из store_measurements
EXPLAIN (ANALYZE, BUFFERS)
SELECT m.measurement_uuid FROM measurements m
 WHERE m.measurement_uuid IN (<СПИСОК>);

-- шаг 3: тот же запрос с границей по времени, как его предлагает переписать K6
EXPLAIN (ANALYZE, BUFFERS)
SELECT m.measurement_uuid FROM measurements m
 WHERE m.measured_at >= now() - interval '31 days'
   AND m.measurement_uuid IN (<СПИСОК>);
```

Смотрим: число узлов `Index Scan` по чанкам. Их столько же, сколько чанков в таблице, —
подтверждение K6: отсечения нет. Разница в числе чанков и в `shared read` между шагами 2 и 3
— это и есть цена вопроса; её и нести лиду.
