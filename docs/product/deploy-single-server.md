# Развёртывание стенда на одном сервере (1 vCPU, 2 ГБ)

Инструкция для **ИИ-агента**, который разворачивает «Мониторинг интернета ВКО» на одной
виртуальной машине: панель, API, база, серверы замеров, Prometheus и Grafana — всё на этом же
хосте. Стенд демонстрационный и для замеров, боевой нагрузки на нём нет.

Не путать с `docs/product/agent-install.md`: там «агент» — это служба `vko-agent` на школьном
ПК. Здесь «агент» — ассистент, который выполняет развёртывание.

Человеку, который ставит систему руками, нужна не эта страница, а
[`admin-guide.md`](admin-guide.md): она короче и не знает про ограничения одного ядра. Здесь —
то же самое, но с проверками после каждого шага, с бюджетом памяти и с обходами известных
дефектов (`docs/known-limitations.md`).

---

## 0. Границы: что агент делает сам, а что отдаёт человеку

Правила из `AGENTS.md` действуют и здесь. Технически закрыты (`.claude/settings.json`) и потому
выполняются **человеком**, агент только готовит команду и объясняет, что она делает:

| Закрыто для агента | Что из этого следует |
|---|---|
| `sudo` | всё root-ское — swap, пакеты, docker, firewall, systemd — готовит агент, запускает человек |
| `ssh`, `scp`, `rsync` | агент работает **в сессии на самом сервере**; развернуть удалённо со своей машины он не может |
| чтение и правка `.env` | агент даёт готовый текст переменных и команды генерации секретов, вписывает их человек |
| `docker compose down -v`, `docker volume rm`, `docker system prune` | том с базой не трогается никогда; перезапуск — только `restart` / `up -d` |
| `alembic downgrade`, `alembic stamp` | миграции forward-only; сломанную миграцию чинит разработчик новой ревизией |

Спрашивать человека и не решать самому (`AGENTS.md` §1, §2.5): правка `docker-compose.yml`,
`deploy/*`, `Makefile`, установка зависимостей, любой шаг на **боевом** сервере. Этот стенд —
тестовый и демонстрационный, поэтому агент действует сам, но подтверждение человека в той же
сессии нужно на каждое действие, которое выходит за пределы каталога проекта.

Со стенда **ничего не коммитится и не пушится**. `.env`, `docker-compose.override.yml`, дампы и
журналы — файлы этой машины, в репозиторий они не попадают (§3.4).

## 1. Что поднимается и сколько это ест

Одиннадцать сервисов `docker-compose.yml`. Память измерена 2026-09-22 на холостом ходу, на
настоящих образах этого репозитория (`docker stats --no-stream`), поэтому это ориентир под
нагрузкой в ноль, а не предел:

| Сервис | Память на холостом ходу | Наружу | Зачем |
|---|---|---|---|
| `db` | 372 МиБ | нет | PostgreSQL 16 + TimescaleDB + PostGIS |
| `grafana` | 247 МиБ | нет (loopback) | графики сервера |
| `prometheus` | 128 МиБ | нет | метрики API и воркера |
| `worker` | **101 МиБ при `--concurrency=1`** | нет | Celery: инциденты, уведомления, выгрузки |
| `api` | 90 МиБ | через Caddy | FastAPI |
| `beat` | 86 МиБ | нет | расписание Celery |
| `speedtest` | 61 МиБ | **да, 8080** | LibreSpeed — основной сервер замера |
| `web` | 18 МиБ | через Caddy | nginx со сборкой панели |
| `redis` | 10 МиБ | нет | брокер Celery, счётчик лимитов |
| `ndt7` | 3 МиБ | **да, 8081** | резервный сервер замера |
| `caddy` | ~30 МиБ (не измерено) | **да, 80 и 443** | TLS и реверс-прокси |

Итого около **1,15 ГиБ в покое**. На 2 ГБ это работает, но без запаса, поэтому обязательны два
условия: swap (§2) и явный `--concurrency=1` у воркера (§6). Без второго Celery берёт число
рабочих процессов по числу ядер — на тестовой 16-ядерной машине тот же воркер занимал **857
МиБ** вместо 101.

Самый прожорливый момент — не работа, а **сборка образа панели** (`npm ci` + `vite build`).
Её проходят один раз и со swap.

## 2. Шаги человека до начала (root)

Агент готовит эти команды, выполняет человек. После каждого блока — проверка, её выполняет
агент.

**2.1 Операционная система.** Рекомендуется Ubuntu 24.04 LTS или Debian 12: на них нет SELinux,
а с ним связан открытый дефект T-74 (§8). На Fedora / Rocky / AlmaLinux / RHEL развернуть тоже
можно, но §8 обязателен.

**2.2 Swap 4 ГБ** — без него сборка панели падает по памяти:

```bash
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -w vm.swappiness=10 && echo 'vm.swappiness=10' > /etc/sysctl.d/99-swappiness.conf
```

Проверка: `free -m` показывает 4096 в строке Swap.

**2.3 Docker Engine и плагин compose** — по инструкции docs.docker.com для своего дистрибутива
(не пакет `docker.io` из старых репозиториев: нужен `docker compose` версии 2.24+, §6 опирается
на тег `!override`). Затем пользователю, под которым будет работать агент:

```bash
usermod -aG docker <пользователь>
```

Проверка (в новой сессии, чтобы группа применилась): `docker compose version` — 2.24 или выше,
`docker run --rm hello-world` отрабатывает без `sudo`.

**2.4 Часовой пояс и время.** `timedatectl set-timezone Asia/Almaty`, NTP включён
(`timedatectl` → `System clock synchronized: yes`). Замеры хранятся в UTC, но расписание слотов
и рабочие часы школ считаются в поясе системы, а сервер с уехавшими часами отклоняет замеры как
слишком старые.

**2.5 Сеть.** A-запись домена на адрес сервера **до** первого запуска Caddy: сертификат
Let's Encrypt он берёт сам, но только если домен уже указывает сюда и порты 80 и 443 доступны
из интернета.

Firewall: наружу открыть **22, 80, 443** (панель и API) и **8080, 8081** — к ним ходят агенты
школ напрямую, мимо Caddy. Закрыть **8000** (API), **5173** (nginx панели), **5432**, **6379**,
**3000**.

> **Ловушка.** `ufw` и `firewalld` **не закрывают** порты, опубликованные Docker: правила
> `DOCKER` в `iptables` стоят раньше. Поэтому 8000 и 5173 закрываются не firewall'ом, а
> привязкой к `127.0.0.1` в §6. Проверять снаружи: `curl http://<домен>:8000/api/health` с
> другой машины должен **не** отвечать.

**2.6 Диск.** От 20 ГБ. История замеров растёт: 360 000 замеров симулятора — это сотни мегабайт
с индексами, а WAL и образы Docker занимают больше самой базы.

## 3. Репозиторий и `.env`

```bash
git clone git@github.com:saylaukhan/codemasters.git
cd codemasters
git checkout developing        # если лид уже слил в main — тогда main, спросить
```

`.env` создаёт и заполняет **человек** (`cp .env.example .env`), агент его не читает и не
правит. Агент даёт значения и объясняет каждое; остальные строки `.env.example` остаются как
есть.

| Переменная | Что вписать | Почему это важно именно здесь |
|---|---|---|
| `POSTGRES_PASSWORD` | своё, без пробелов, `$` и `#` | эти же символы читает `make`, кавычки ломают `db-reset` |
| `DATABASE_URL` | `postgresql+asyncpg://vko:<пароль>@localhost:5432/vko_monitor` | внутри compose хост подменяется на `db` сам |
| `SECRET_KEY` | `openssl rand -hex 32` | смена разлогинивает всех |
| `API_BASE_URL` | `https://<домен>` | **от схемы зависит флаг `Secure` у refresh-cookie**: с `https` в переменной вход по `http://<ip>` не сохранит сессию |
| `CADDY_DOMAIN` | `<домен>` | `localhost` даст самоподписанный сертификат, агенты его не примут |
| `SPEEDTEST_URL` | `http://<домен>:8080` | **не `localhost`**: адрес уходит агентам школ |
| `NDT7_URL` | `ws://<домен>:8081` | то же; пусто — работать без резерва |
| `TZ` | `Asia/Almaty` | пояс отчётов |
| `GRAFANA_ADMIN_PASSWORD` | своё | по умолчанию `admin` |
| `LLM_API_KEY` | ключ Claude API или DeepSeek (по `LLM_PROVIDER`) или пусто | пусто — AI-черновик обращения недоступен, остальное работает |
| `TELEGRAM_BOT_TOKEN`, `SMTP_*` | по обстоятельствам | пусто — канал отключён, попытка пишется в журнал как «пропущено» |

`SPEEDTEST_URL` и `NDT7_URL` попадают в таблицу `settings` **один раз**, при первом `seed`
(§5). Если база уже наполнена, правка `.env` ничего не изменит — адреса меняются в админке,
вкладка «Настройки».

Проверка: `test -f .env && echo есть`. Содержимое агент не печатает и не цитирует (`AGENTS.md`
§2.7).

## 4. Сборка образов

Самый тяжёлый шаг. Собирать, пока ничего лишнего не запущено:

```bash
docker compose build api web
```

Проверка: команда завершается `exit 0`, `docker images` содержит `vko-monitor-backend` и
`vko-monitor-web`. Проверено 2026-09-22: оба образа собираются с нуля без правок.

Если сборка панели убита по памяти (`Killed`, `JavaScript heap out of memory`) — swap из §2.2
не включён или его меньше 4 ГБ. Проверить `free -m` и повторить; трогать `web/Dockerfile` для
этого не нужно.

## 5. База: схема и справочники

```bash
docker compose up -d db redis
docker compose ps            # db и redis — healthy, база ждёт до минуты
docker compose run --rm api alembic upgrade head
docker compose run --rm api python -m app.seed
```

Ожидаемо: `upgrade` доходит до головы цепочки (на 2026-09-22 это `d4f8b2e6c917`), `seed`
печатает строку вида

```text
seed: районов и городов — 13, провайдеров — 3, типов подключения — 5, тестовых школ — 356;
создано линий — 356, точек мониторинга — 356; системные настройки — созданы;
создано dev-пользователей — 5; праздников РК в календаре — 20
```

Оба шага идут **в контейнере**: хостовые `make migrate` и `make seed` требуют `backend/.venv`,
Python 3.12 и Node на самой машине — на стенде они не нужны. Проверено 2026-09-22.

Истории замеров `seed` не создаёт: школы будут «Нет данных», пока не придёт первый замер от
агента или симулятора (§10).

Если `upgrade` падает на `Multiple head revisions` — это не дело стенда: остановиться и отдать
вывод разработчику (`AGENTS.md` §9).

## 6. Оверрайд под 1 vCPU и 2 ГБ

`docker-compose.yml` не правится: он общий для всех установок, и его изменение требует согласия
человека (`AGENTS.md` §1). Всё, что нужно этой машине, живёт в
`docker-compose.override.yml` — Compose подхватывает его сам, рядом с основным файлом.

Файл этой машины, в репозиторий не попадает. В `.gitignore` его нет, поэтому сразу исключить
локально, не трогая общий файл:

```bash
echo 'docker-compose.override.yml' >> .git/info/exclude
```

```yaml
# Стенд 1 vCPU / 2 ГБ. Файл этой машины: в репозиторий не коммитится.
# Тег !override заменяет список целиком (Compose 2.24+), без него ports и command сливаются.
services:
  api:
    # 8000 наружу не нужен: снаружи ходят через Caddy, а firewall порты Docker не закрывает.
    ports: !override
      - "127.0.0.1:8000:8000"
    mem_limit: 320m

  web:
    ports: !override
      - "127.0.0.1:5173:80"
    mem_limit: 64m

  worker:
    # Без --concurrency Celery берёт число процессов по числу ядер; на стенде нужен ровно один.
    # --max-tasks-per-child возвращает память после тяжёлых выгрузок.
    command: !override
      - celery
      - -A
      - app.workers.celery_app
      - worker
      - --concurrency=1
      - --max-tasks-per-child=200
      - --loglevel=info
    mem_limit: 384m

  beat:
    mem_limit: 128m

  prometheus:
    # 30 суток метрик стенду не нужны.
    command: !override
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.path=/prometheus
      - --storage.tsdb.retention.time=7d
    mem_limit: 256m

  grafana:
    mem_limit: 320m

  db:
    mem_limit: 768m
```

Проверка: `docker compose config` отрабатывает без ошибки, а в его выводе у `api` ровно одна
строка портов и в ней `host_ip: 127.0.0.1`.

**Настройки PostgreSQL** задаются не файлом, а самой базой — тогда они переживают перезапуск и
не требуют правки compose:

```bash
docker compose exec -T db psql -U vko -d vko_monitor <<'SQL'
ALTER SYSTEM SET shared_buffers = '256MB';
ALTER SYSTEM SET effective_cache_size = '768MB';
ALTER SYSTEM SET maintenance_work_mem = '64MB';
ALTER SYSTEM SET work_mem = '8MB';
ALTER SYSTEM SET max_connections = '50';
SQL
docker compose restart db
```

Проверка: `docker compose exec -T db psql -U vko -d vko_monitor -c 'SHOW shared_buffers'` — 256MB.

## 7. Полный стек

```bash
docker compose up -d
docker compose ps
```

Проверки по порядку, каждая со своим ожидаемым ответом:

| Что | Команда | Ожидается |
|---|---|---|
| Все сервисы живы | `docker compose ps` | одиннадцать строк `Up`, `db` и `redis` — `healthy`, ни одного `Restarting` |
| Сертификат | `docker compose logs caddy \| tail -20` | строка про полученный сертификат для домена, без повторяющихся ошибок ACME |
| API снаружи | `curl -s https://<домен>/api/health` | `{"status":"ok", …}` |
| Панель | открыть `https://<домен>` | экран входа; вход `admin@example.kz` / `Password1` |
| Порт API закрыт | с другой машины `curl http://<домен>:8000/api/health` | нет ответа |
| Сервер замеров | `curl -sI http://<домен>:8080/` | `200` |
| Память | `free -m` | использовано меньше 1,6 ГБ, swap почти не тронут |

**Панель открывается только через Caddy.** Клиент ходит на относительный `/api`
(`web/src/api/client.ts`), поэтому по `http://<ip>:5173` API не найдётся — это не поломка.

## 8. Если на хосте SELinux (Fedora, Rocky, Alma, RHEL)

Открытый дефект **T-74**: тома репозитория смонтированы без суффикса `:z`, и на хосте с
`SELinux=Enforcing` `prometheus` уходит в `Restarting` с `permission denied`, а `grafana`
поднимается молча и провижинит **ноль** дашбордов и ноль источников данных — в её журнале при
этом бодрое «finished to provision dashboards».

Проверить: `getenforce`. Если `Enforcing` — добавить в тот же `docker-compose.override.yml`:

```yaml
  prometheus:
    volumes: !override
      - ./deploy/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro,z
      - prometheus_data:/prometheus

  grafana:
    volumes: !override
      - ./deploy/grafana/provisioning:/etc/grafana/provisioning:ro,z
      - ./deploy/grafana/dashboards:/var/lib/grafana/dashboards:ro,z
      - grafana_data:/var/lib/grafana

  caddy:
    volumes: !override
      - ./deploy/Caddyfile:/etc/caddy/Caddyfile:ro,z
      - caddy_data:/data
      - caddy_config:/config
```

Проверка: после `docker compose up -d` `prometheus` не перезапускается, а в Grafana (§9) виден
дашборд «Сервер мониторинга ВКО» и источник `vko-prometheus`.

Сам `docker-compose.yml` при этом не трогается: `:z` в нём — задача T-74, её делает разработчик.

## 9. Что настроить сразу после первого входа

Порядок из `admin-guide.md` §4; здесь только то, что специфично для стенда.

1. **Адреса серверов замеров.** «Администрирование → Настройки»: «Адрес LibreSpeed» —
   `http://<домен>:8080`, «Адрес ndt7» — `ws://<домен>:8081`. Если в них остался `localhost`,
   агенты школ будут мерить сами себя. Это единственное место, где адрес правится после seed.
2. **Учётные записи.** Пять dev-пользователей из seed (`admin@`, `oblast@`, `rayon@`,
   `school@`, `provider@`, пароль `Password1`) — только для демонстрации. Для показа они нужны:
   сценарии `demo-scenario.md` написаны под них. Если на стенд попадут настоящие данные школ —
   завести живых людей во вкладке «Пользователи» и тестовых **заблокировать**, не удалять
   (история сохраняется, ТЗ п. 16).
3. **Grafana** — `http://127.0.0.1:3000` только с самого сервера, наружу не публикуется.
   Смотреть через туннель: `ssh -L 3000:127.0.0.1:3000 <пользователь>@<домен>` — команду
   выполняет человек со своей машины, у агента `ssh` закрыт. Пароль — из `.env`.
4. **Пороги, расписания, правила инцидентов** — значения по умолчанию рабочие. Для показа их
   меняют по `demo-scenario.md` §2.2, и **накануне**, а не за полчаса: новые интервалы агент
   получает только на следующем обращении за конфигурацией.

## 10. Тестовые данные

**Не запускать на этой машине `make simulate n=1000 days=90`.** Это 360 000 замеров и около
50 минут только на регистрацию (лимит `AGENT_REGISTER_RATE_LIMIT` — 20 в минуту), а на 350
школах и 90 сутках `GET /api/analytics` уже на машине разработчика давал p95 ≈ 4,9 с при
бюджете 3 с (открытый дефект **T-72**). На одном ядре будет заметно хуже.

Для стенда:

```bash
SIM_ADMIN_PASSWORD='<пароль admin@example.kz>' \
  python3 simulator/simulate.py --schools 60 --devices 120 --days 30 --api https://<домен>
```

Это ориентир: около 14 000 замеров, карта и аналитика остаются отзывчивыми, все четыре статуса
ТЗ п. 13 в данных есть — профили выдаются школам по циклу, поэтому статусы появляются даже на
маленьком прогоне.

Что важно знать про симулятор (`simulator/README.md`):

- Он ходит по API и живёт на **стандартной библиотеке Python 3.12+**, но в образ backend не
  входит. Либо поставить python3 на сервер, либо запускать с ноутбука против `--api https://<домен>`.
- На время прогона он поднимает системную настройку «Срок очереди агента» до `--days` и
  возвращает прежнее значение в конце — в том числе после Ctrl+C. Убитый `kill -9` оставит её
  поднятой: вернуть в админке.
- **Данные «живут» `offline_after_s` после прогона** (по умолчанию 900 с). Приём замеров не
  двигает `last_seen_at`, его двигает heartbeat, а его симулятор шлёт один раз в конце. Через
  15 минут все школы читаются как «Нет соединения», а `worker` заведёт инцидент на каждую
  линию. Поэтому: либо прогон непосредственно перед показом, либо на время показа поднять «Нет
  соединения после, с» в админке.
- `worker` и `beat` должны быть подняты: без них не будет ни инцидентов, ни признака
  несоответствия договору (пересчёт раз в 15 минут).

## 11. Замеры на этом же сервере: чего ждать от 1 vCPU

LibreSpeed на одном ядре — сам по себе ограничитель: измеренная скорость упрётся в процессор и
канал стенда раньше, чем в канал школы. Для демонстрации и для школьных линий это приемлемо, но
цифры со стенда нельзя выдавать за паспортную скорость сервера замеров.

Два замера одновременно делят одно ядро, и оба покажут меньше. Расписание разводит агентов
случайным смещением внутри слота, но на показе не стоит запускать симулятор и живой замер
одновременно.

LibreSpeed и ndt7 работают **без TLS** (`http://`, `ws://`) и опубликованы напрямую, мимо
Caddy — известное ограничение, решение по сертификату для них принимает лид.

## 12. Агент на школьном ПК

MSI зашивает адрес сервера при сборке: вход workflow, переменная репозитория
`AGENT_SERVER_URL` или запасное `https://monitor.example.kz`. Поэтому либо задать
`AGENT_SERVER_URL=https://<домен>` до сборки поставки, либо всегда ставить с параметром:

```text
msiexec /i VKO-Agent.msi SERVER_URL=https://<домен> ENROLLMENT_CODE=<код из админки>
```

Код установки одноразовый, привязывает один ПК к одной школе и показывается **ровно один раз**.
Проверка на самом ПК — `vko-agent status`: служба запущена, устройство зарегистрировано,
«Очередь на отправку: 0». Подробности — `docs/product/agent-install.md`.

Установка на живом Windows ни разу не проверялась (T-49) — закладывать на первый ПК время с
запасом и снимать вывод `sc qc VKOMonitorAgent` и `sc qfailure VKOMonitorAgent`.

## 13. Бэкап

**`docker-compose.backup.yml` на этом стенде не поднимать.** Открытый дефект **T-76**:
pgBackRest на образе `timescale/timescaledb-ha:pg16` не снимает ни одного бэкапа, контейнер
уходит в `Restarting`, а `archive_mode=on` при этом копит WAL и тихо съедает диск — на 20 ГБ
это заметят быстро.

Для стенда достаточно суточного дампа. Команда (выполняет человек, потому что складывает файл
вне каталога проекта):

```bash
docker compose exec -T db pg_dump -U vko -Fc vko_monitor > /var/backups/vko-$(date +%F).dump
```

Восстановление на TimescaleDB идёт не обычным `pg_restore`, а с двумя вызовами вокруг него —
иначе гипертаблицы не восстановятся:

```sql
CREATE DATABASE vko_restore;
\c vko_restore
CREATE EXTENSION timescaledb;
SELECT timescaledb_pre_restore();
-- pg_restore -U vko -d vko_restore /var/backups/vko-….dump
SELECT timescaledb_post_restore();
```

Восстанавливаться **на запасную базу**, а не поверх рабочей. Бэкап, из которого ни разу не
восстанавливались, бэкапом не считается: один прогон — до показа.

## 14. Смоук-лист перед показом

Проходится целиком, занимает минут десять.

1. `docker compose ps` — одиннадцать `Up`, ни одного `Restarting`; `free -m` — swap не
   разрастается.
2. Вход всеми пятью учётками по очереди.
3. `/overview`, `/map`, `/schools`, `/analytics`, `/incidents`, `/exports` — ни одного пустого
   экрана и ни одной ошибки в консоли браузера.
4. Карточка школы → карточка ПК → замер: в замере есть снимок порогов.
5. Выгрузка XLSX: 11 колонок минимального набора ТЗ п. 9 на месте.
6. Grafana через туннель: дашборд «Сервер мониторинга ВКО» рисует данные, а не «No data»
   (кроме панели «Доля ошибочных ответов за час» — у неё известный дефект T-75).
7. Симулятор прогнан, либо «Нет соединения после, с» поднято на время показа (§10).

Полный сценарий демонстрации — `docs/product/demo-scenario.md`, там же лист прогона.

## 15. Что делать, когда не работает

Общая таблица симптомов — `admin-guide.md` §11. Специфичное для одного сервера:

| Признак | Причина и что делать |
|---|---|
| Контейнер `Killed` / `OOMKilled` | кончилась память: проверить `--concurrency=1` у воркера (§6) и swap (§2.2); временно остановить `prometheus` и `grafana` |
| Сборка панели падает на `npm ci` или `vite build` | тот же swap; остальные контейнеры на время сборки остановить |
| Caddy не берёт сертификат | DNS ещё не указывает на сервер, либо 80 и 443 закрыты снаружи; в журнале Caddy видно, на каком шаге ACME остановился |
| Вход проходит, но через минуту выкидывает | схема в `API_BASE_URL` не совпадает с тем, как открыли панель: cookie выдана с `Secure`, а страница открыта по `http` |
| `prometheus` перезапускается, в Grafana нет дашбордов | SELinux, §8 |
| Панель по `:5173` не показывает данные | так и задумано: клиент ходит на относительный `/api`, нужен Caddy (§7) |
| Аналитика открывается 5 секунд | известный дефект T-72; на стенде лечится размером данных (§10) |
| Все школы вдруг «Нет соединения» | прошло `offline_after_s` после прогона симулятора (§10) |
| В журнале аудита у всех один и тот же IP | адрес контейнера Caddy — известное ограничение, `--forwarded-allow-ips` не задан |

Правило прежнее: команда упала — показать её вывод человеку, а не обходить (`AGENTS.md` §9).

## 16. Чего на стенде не делать

- `docker compose down -v`, `docker volume rm`, `docker system prune` — уносят базу вместе с
  историей замеров.
- Править `docker-compose.yml`, `deploy/*`, `Makefile` под этот сервер: всё, что нужно одной
  машине, живёт в `docker-compose.override.yml` (§6).
- Коммитить и пушить со стенда: `.env`, оверрайд, дампы и журналы — файлы этой машины.
- Гонять симулятор на установке с живыми школами: он поднимает и возвращает настройку срока
  очереди на всю систему и подрежет очереди настоящих агентов.
- Выдавать непроверенное за проверенное: «развернул» пишется после того, как §7 и §14 пройдены
  с настоящим выводом команд.
