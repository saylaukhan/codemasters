# Система автономного мониторинга интернета ВКО
### Декомпозиция технического задания и архитектурный гайд для сборки MVP

**Блоки:** [Edge-Агенты] · [REST API] · [AI-Генерация] · [Web-Дашборд]

---

## Слайд 2. Глобальная задача: исключить ручной фактор

**Ручной контроль**
- Случайные замеры, зависимость от персонала
- Человеческий фактор
- Искаженные данные

**Автономный мониторинг**
- Объективная статистика 24/7 без участия пользователя
- Фоновый агент
- Центральная БД

> Границы проекта охватывают полный цикл: от фоновой службы на школьном ПК до интерактивной панели на столе руководителя управления образования.

---

## Слайд 3. Высокоуровневая архитектура (The Blueprint)

**Блок 1: Edge (Школы)**
- Клиентский агент (Служба/Daemon)
- Локальный кэш данных

**Блок 2: Backend (Транспорт и Хранение)**
- Защищенный канал (VPN/TLS)
- API → REST API
- База данных (PostgreSQL/MySQL)
- Обработка инцидентов

**Блок 3: Frontend (Пользователи)**
- Веб-панель
  - Интерактивная Карта
  - Аналитика
  - Экспорт
  - AI-Генератор

> Данная архитектура должна обеспечивать масштабируемость на сотни организаций и идемпотентность передачи данных.

---

## Слайд 4. Крайний узел сети: Клиентский агент

**Топология**
- Подключение по Ethernet максимально близко к границе сети.
- Обязательное постоянное питание.
- Запрет на случайный Wi-Fi.

**Автономность**
- Запуск как фоновая служба ОС.
- Полное отсутствие GUI для конечного пользователя.

**Расписание и Защита**
- Замеры 3-5 раз в день.
- Обязательное рандомизированное смещение времени для защиты от синхронных DDoS-атак.

**Отказоустойчивость**
- При обрыве связи: Локальное кэширование -> Авто-отправка при восстановлении сети.

---

## Слайд 5. Базовые пороги и метрики (Target Metrics)

- Download ≥ 20 Мбит/с
- Upload ≥ 20 Мбит/с
- Ping ≤ 100 мс
- Jitter ≤ 30 мс
- Packet Loss ≤ 2%
- Uptime ≥ 99%

**Метаданные**
Обязательные метаданные пакета: Device ID, School ID, Timestamp, Версия агента.

⚠️ Пороги должны быть настраиваемыми администратором, а не зашиты в код.

## Слайд 6. Бэкенд: Структура данных и API-контракт

**Структура данных:**
- **Schools**: id, название, район
- **Devices**: id, school_id, кабинет, статус, версия
- **Measurements**: id, device_id, timestamp, скорости, ping, jitter, loss

**API-контракт:**
- `POST /api/measurements`
- `POST /api/devices/register`
- `GET /api/schools/{id}`
- `GET /api/analytics`

> Идентификаторы оборудования защищены от подмены. Передача строго через VPN/HTTPS.

## Слайд 8. Drill-down аналитика: От области к кабинету

**Уровень 1: Карта** — фильтры (Район, Поставщик, Тип подключения, Период)

**Уровень 2: Карточка Школы**
- School ID, Провайдер, Текущий статус, Заявленная скорость vs Фактическая
- Графики просадок по времени суток
- Контакты ответственного лица
- История инцидентов
- Список ПК

**Уровень 3: Устройство (ПК)**
- Кабинет, Device ID, история замеров конкретной машины, статус активности

## Слайд 10. Жизненный цикл инцидента

1. **Триггер** — Последовательность замеров ниже порога (фильтрация единичных сбоев)
2. **Создание** — Автоматическое или ручное открытие карточки. Статус «Новый»
3. **Передача** — Отправка провайдеру. Статусы «Передан поставщику» → «В работе»
4. **Устранение** — Возврат метрик в норму + подтверждение. Статусы «Устранен» → «Закрыт»

> В карточке инцидента фиксируется точное время начала и конца сбоя для расчета фактического времени простоя.

## Слайд 11. Умная автоматизация: AI-генерация обращений

**Входящие данные:**
- School ID, Провайдер, фактические метрики, порог просадки, период проблемы

**AI Обработка:**
- LLM-движок анализирует массив сбоев

**Исходящий документ:**
- Сгенерированный черновик официальной претензии провайдеру
- Валидация: Пользователь проверяет, редактирует и нажимает «Отправить»

---

## Слайд 12. Экспорт результатов и отчетность

- **XLSX / CSV (Обязательно для MVP)** — Сырые массивы данных. Фильтры: школа, период, статус, кабинет
- **PDF (Желательно)** — Готовый форматированный отчет по конкретной школе (графики + таблица отключений)
- **JSON (Опционально)** — Для машинной интеграции с внешними аналитическими системами

> Выгрузка должна включать микро-метрики вплоть до Jitter и Packet Loss.

## Слайд 13. Технологический стек и Безопасность

**Рекомендуемый стек (Гибкий выбор)**
- Agent: C# / .NET, Python, Go, Java
- Backend: Node.js, FastAPI, Spring, .NET
- Frontend: React, Vue, Angular
- DB: PostgreSQL, MySQL

**Правила безопасности (Строгие ограничения)**
- VPN или TLS/HTTPS канал обязателен.
- Отсутствие сбора персональных данных (учеников/учителей).
- Уникальная авторизация узлов (запрет подмены School ID).

## Слайд 14. Требования к поставке MVP (Checklist)

- [DONE] Автономный клиентский агент (запускается сам)
- [DONE] Сервер, API и База данных
- [DONE] Веб-панель с Картой ВКО и аналитикой
- [DONE] Логика инцидентов и AI-генерация писем
- [DONE] Экспорт в XLSX/CSV
- [DONE] Документация: Инструкция админа, Архитектура, Описание API

> **Критическое требование:** Продукт должен запускаться без участия разработчиков. Конфигурации вынесены в настройки (hardcode запрещен).

## Слайд 15. Критерии приемочных испытаний (Scoring)

- 30 баллов: Работоспособность базового функционала
- 15 баллов: Точность замеров и стабильность агента
- 15 баллов: Веб-панель, Карта и аналитика
- 10 баллов: Ролевая модель и безопасность
- 10 баллов: Учет инцидентов
- 20 баллов: AI-функции, архитектура, UX и отказоустойчивость

> Оценивается фактическая работоспособность. Презентация интерфейса без работающего кода не оценивается.
