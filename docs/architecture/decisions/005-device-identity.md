# ADR-005 · Идентичность устройства и защита от подмены

**Статус:** принято · **Дата:** 2026-09-16 · **Источник:** ТЗ п. 12, п. 2, п. 20, plan.md §4.1, §13

## Контекст
ТЗ п. 12: у каждого устройства уникальный идентификатор и авторизация; сервер проверяет принадлежность
Device ID школе; нужна защита от подмены School ID и Device ID; секреты не хранятся в открытом виде.
При этом п. 2 предлагает передавать School ID вместе с замером — а всё, что пришло в запросе, можно
подделать. Регистрацию по одному School ID, как в Giga Meter (plan.md §1), поэтому не берём.

## Решение
- Регистрация по одноразовому коду: админ выдаёт код для школы (действует 7 дней), хранится в
  `enrollment_codes` (`code_hash`, `school_id`, `expires_at`, `used_at`). Агент при первом старте вызывает
  `POST /api/devices/register` и получает `device_id` и `device_token`; при тихой установке код передаётся
  параметром `ENROLL_CODE` (plan.md §4.1).
- `device_token` на сервере — только хэш (`devices.token_hash`), сам токен не хранится нигде; на клиенте —
  Windows DPAPI, на Linux — файл с правами 600 (`agent/internal/secure/`). Каждый запрос агента —
  `Authorization: Device <token>`.
- **Уточнено 2026-09-21 (T-56):** хэш токена — `sha256` со сравнением за постоянное время, а не argon2id.
  Случайная часть токена — 256 бит (`secrets.token_urlsafe(32)`): подбирать нечего, и стоимость argon2 —
  19 МиБ и десятки миллисекунд в event loop на каждом запросе каждого агента — не покупает здесь ничего.
  Argon2id остаётся там, где секрет может угадать человек: пароли панели и код установки (50 бит).
  Алгоритм назван в самой строке (`sha256$…`); строка, записанная раньше, принимается по-прежнему и
  заменяется при первом же запросе своего агента — миграцией это сделать нельзя, токена у сервера нет
  (`backend/app/core/security.py`, `backend/app/core/deps.py`).
- School ID и линия никогда не берутся из запроса: сервер выводит их по цепочке `devices → monitoring_points →
  lines → schools` (ADR-003). В Pydantic-схемах запросов агента полей `school_id` и `school_code` нет.
- Блокировка — `devices.status = blocked` из админки: запросы отклоняются, история замеров сохраняется.
  Ротация токена — по кнопке в админке; порядок доставки нового токена агенту фиксируется в T-36.
- Ошибки авторизации и передачи — в журнал событий; rate limit и валидация диапазонов метрик — T-51.

## Последствия
- Подмену School ID нечем выполнить: поля нет в контракте, привязка живёт только в БД.
- Утечка токена компрометирует одно устройство и лечится блокировкой или ротацией без переустановки.
- DPAPI привязывает токен к машине: копирование файлов агента на другой ПК доступа не даёт.
- Замена хэша необратима: строку, уже переписанную в `sha256$…`, код с argon2 не примет, и устройство
  пришлось бы регистрировать заново. Обратного пути нет по построению — токен на сервере не хранится.
- Школе для установки нужен только код; просроченный код придётся выдать заново.
- Кода нет: сервер — T-14, агент — T-07, админка устройств — T-36.
