# ADR-004 · Статус замера считается на сервере, пороги — снимок в записи

**Статус:** принято · **Дата:** 2026-09-16 · **Источник:** ТЗ п. 11, п. 13, п. 20, plan.md §6

## Контекст
ТЗ п. 11 требует настраиваемые пороги, не зашитые в клиент, и хранение фактических значений вместе с
порогами, применёнными при оценке; п. 13 — четыре статуса с цветовой индикацией; п. 20 — смену порогов
из админки. Если статус считает агент, смена порога требует обновления агентов, а история становится несравнимой.

## Решение
- Агент шлёт только сырые числа: `download_mbps`, `upload_mbps`, `ping_ms`, `jitter_ms`,
  `packet_loss_pct`, `connection_status`. Поля статуса качества в схеме запроса агента нет.
- Сервер при приёме (T-18) берёт профиль из `threshold_profiles`: глобальный, поверх него районный, поверх
  него профиль линии — побеждает самый конкретный; в замер пишет `thresholds_snapshot` (jsonb) и `quality_status`.
  Базовые пороги (п. 11): Download ≥ 20 и Upload ≥ 20 Мбит/с, Ping ≤ 100 мс, Jitter ≤ 30 мс, Packet Loss ≤ 2 %.
- Правила: всё в норме → `normal`; один показатель нарушен не более чем на 30 % от порога → `unstable`;
  несколько показателей или отклонение больше 30 % → `critical`; `connection_status = offline` → `offline`.
  Договор — отдельный флаг `contract_ok` против `lines.contract_down_mbps` / `contract_up_mbps`, на `quality_status` не влияет.
- Статус школы — по 3 последним замерам основной линии (Wi‑Fi-замеры не учитываются) плюс heartbeat:
  нет heartbeat дольше 15 мин в рабочие часы → «Нет соединения»; вне рабочих часов — «Нет данных»
  (`no_data`, только отображение, не статус качества; рабочие часы — ADR-014).
- Коды `normal | unstable | critical | offline | no_data`; подписи в UI — только из `web/src/lib/labels.ts`.
  Смена порогов не пересчитывает историю: каждый замер хранит свой снимок.

## Последствия
- Спор с провайдером решается по записи: факт, пороги и сервер замера лежат рядом (plan.md §16).
- Новый порог из админки действует на следующий замер без переустановки агентов (демо, plan.md §15);
  агент не знает порогов и ничего не оценивает, поэтому проще и реже требует обновления.
- Пересчёт старых статусов по новым порогам, если понадобится, — отдельный ADR.
- N = 3 и 30 % — умолчания, меняются в админке. Кода нет: расчёт — T-18, профили — T-37, статус школы — T-16.
