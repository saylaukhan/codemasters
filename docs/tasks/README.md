# Задачи

Список выведен из ТЗ заказчика (`docs/product/tz.md`, ссылки вида «п. 11») и плана реализации
(`docs/product/plan.md`, ссылки вида «plan.md §6»). Каждая задача двигает пункт ТЗ или этап
плана; если не двигает — её здесь нет.

Как читать задачу: **Зачем** — какой пункт ТЗ и этап плана закрывает и какой ADR действует;
**Где** — папки, таблицы и эндпоинты, с которых начинать (кода в репозитории пока нет: структура
папок появится в T-01, до этого пути ниже — план, а не факт); **Сделано, когда** — проверяемые
критерии, по которым вы и чек-лист `docs/checklist.md` решаете, готово или нет.

Размер: S — до полудня, M — 1–2 дня, L — режется на части, первое слияние — каркас.
Волна: MVP (этапы 0–6 плана, ориентир 6 недель) · v1 (после демо) · позже. Даты ставит лид.

Статусы: `todo | in-progress | done (дата)`. Статус меняет тот, кто берёт задачу; при слиянии
в `developing` он же ставит `done` с датой. Слияние делает человек командой `git merge --no-ff`
после прохождения `docs/checklist.md`; отчёт по задаче — `docs/worklog.md`.

Перед первой задачей прочитайте `CONTRIBUTING.md` и ADR по своей области
(`docs/architecture/decisions/`). Это полчаса, они сэкономят вам день.

## Порядок внутри MVP

Если к демо не успевается всё, недоделанным остаётся то, что ниже по списку, а не то, что
случайно взяли последним:

1. **Сквозной путь данных** — T-01, T-02, T-05, T-06–T-11, T-14–T-18 — пока замер с реального
   агента не виден в БД, остальное не начинаем: всё ниже строится на этих данных и без них
   проверяется только на заглушках.
2. **Увидеть данные** — T-03, T-20, T-21, T-22, T-23, T-24, T-25, T-26, T-19, T-27: карта и
   карточки — первое, что увидит заказчик; данные в БД без панели никому не видны.
3. **Управлять** — T-34–T-39, T-17, T-13, T-04: пороги и расписание должны меняться без кода
   (п. 20), иначе демо-сценарий 4 из plan.md §15 не пройти.
4. **Реагировать** — T-12, T-16, T-40, T-41, T-42, T-44: инциденты и уведомления опираются на
   статусы и heartbeat, а провайдер — участник устранения, а не зритель.
5. **Отчитываться** — T-30, T-31, T-28, T-29, T-32: XLSX и CSV обязательны для MVP (п. 9), но
   им нужны готовые данные и агрегаты.
6. **Обращаться** — T-46, T-47, T-48: обращение собирает контекст из инцидентов и отчётов,
   поэтому идёт после них.
7. **Поставить** — T-49, T-51, T-55, T-57, T-58: MSI, симулятор и документация нужны только к
   демо и переделываются, если менялось что-то выше.

## Решения по умолчанию

Эти вопросы ТЗ оставляет открытыми. Решения приняты, чтобы не блокировать разработку, и
действуют, пока лид не решит иначе. Разработчик не переспрашивает — делает так. Если решение
меняется, лид правит эту таблицу и добавляет новый ADR, который ссылается на старый
(`docs/architecture/decisions/README.md`).

| Вопрос | Решение по умолчанию |
|---|---|
| Канал: VPN или HTTPS (п. 12) | HTTPS/TLS 1.2+ через Caddy + токен устройства. WireGuard — только по требованию заказчика, отдельной задачей |
| Сколько замеров в день (п. 2: 3–5) | 4 слота по умолчанию: 08:30–09:00, 11:00–11:30, 13:30–14:00, 16:00–16:30 (Asia/Almaty); меняется в админке |
| Длительность теста | 10 с на направление; 30 ICMP-пакетов через 200 мс |
| N последних замеров для статуса школы | 3 по основной линии; Wi‑Fi-замеры не учитываются |
| «Нет соединения» по heartbeat | нет heartbeat дольше 15 мин в рабочие часы; вне рабочих часов — «Нет данных» |
| Рабочие часы школы | 08:00–18:00, пн–сб, Asia/Almaty; настраивается на школу |
| Нестабильно / Критично (п. 11) | один показатель нарушен не более чем на 30 % → «Нестабильно»; несколько показателей или отклонение больше 30 % → «Критично»; проценты — в админке |
| Правило инцидента по умолчанию (п. 18) | 3 нарушения подряд или 30 минут; закрытие после 2 нормальных подряд; «Устранён» → «Закрыт» автоматически через 24 ч |
| Устойчивое несоответствие договору (п. 14) | больше 50 % замеров основной линии за 7 дней ниже договорной скорости |
| Доступность (п. 11) | 1 − простой / время наблюдения по рабочим часам; простой = `outages` + пропуски heartbeat |
| Хранение | сырые замеры 24 месяца, агрегаты бессрочно; очередь агента 30 дней / 10 000 записей |
| Фоновая выгрузка | больше 10 000 строк или PDF → Celery, файл по ссылке, хранится 7 дней |
| LLM | Claude API через адаптер `LLMProvider`; Ollama — вариант для закрытого контура |
| Язык интерфейса | русский; казахский — «позже»; без i18n-фреймворка, строки в компонентах, статусы — из `labels.ts` |
| Подпись MSI | нужен сертификат Authenticode от заказчика; до него MSI без подписи, риск в known-limitations |
| School ID | `schools.school_code` — строка от заказчика; если нет — `VKO-<код района>-<номер>` |
| Кто настраивает пороги (п. 16 vs п. 20) | Область — пороги, расписания, правила инцидентов, справочники; Администратор — то же плюс пользователи, устройства, релизы агента, журналы |
| Кто закрывает инцидент | пользователь области/района или автоматически через 24 ч после «Устранён» |
| Email обращений | SMTP заказчика; до настройки — PDF сохраняется, обращение помечается «не отправлено» |
| Карта-подложка | MapLibre + публичные OSM-тайлы на демо; свой tileserver — позже |
| Несколько устройств на линии | статус линии — по всем её Ethernet-устройствам; точка `is_primary` — главная |
| Переходы между статусами инцидента (п. 19) | вперёд с пропуском промежуточных; назад — только «Ожидает информации» → «В работе» и «Устранён» → «В работе»; из «Закрыт» — никуда (T-41) |
