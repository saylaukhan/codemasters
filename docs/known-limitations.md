# Известные ограничения

Это список того, что заведомо не доделано. Он нужен, чтобы вы или ИИ-агент не приняли
недоделанное за баг и не полезли чинить то, что решено оставить как есть. Это не план работ:
планы — в `docs/tasks/README.md`, решения — в `docs/architecture/decisions/`.

| Ограничение | Влияние | Что делать |
|---|---|---|
| Есть только каркас (T-01), схема БД v1 (T-02) и контракт API всех эндпоинтов plan.md §10 (T-03); функции ТЗ не реализованы | ни одна функция ТЗ не работает; эндпоинты в `backend/app/api/` — заглушки, отвечают 501 `not_implemented` с номером задачи реализации; токен устройства и JWT только объявлены в OpenAPI, не проверяются; папки внутри `agent/internal/`, `web/src/pages/` в документах — план, а не факт | реализация — задача из ответа 501; проверка токенов — T-14, T-20; статусы задач — `docs/tasks/README.md` |
| Эндпоинтов, которых нет в plan.md §10, в контракте нет, хотя задачи их называют: полигоны районов для карты (T-04, T-22), справочники районов, провайдеров и типов подключения для фильтров всех ролей — сейчас только в `/api/admin` (T-22, T-24), список устройств, перепривязка устройства к точке, ротация токена (T-36), точки мониторинга (T-35), замеры школы для вкладки карточки (T-25), список и карточка обращений (T-48), список выгрузок (T-33), журнал уведомлений (T-39), выбор ответственного за инцидент (T-41), загрузка MSI релиза (T-50) (T-03) | панель не получит полигоны районов и не сможет управлять точками и устройствами, пока эндпоинт не добавлен | решает лид; эндпоинт добавляет задача, которой он нужен, — правкой схем и `make openapi` в том же слиянии (ADR-009) |
| Для роли провайдера не определено, из какой линии берутся поля школы уровня «основная линия» (статус, средние, поставщик, договор, последний замер), если у провайдера только резервная линия школы (T-03) | без правила реализация может показать провайдеру данные чужой линии (ТЗ п. 16) или пустую карточку | T-20 и T-44: зафиксировать правило в описании полей контракта и тестом «провайдер не видит чужую линию» |
| `working_hours` школы есть в контракте (`SchoolDetail`, `SchoolUpdate`), но не в схеме БД (T-03) | рабочие часы нельзя сохранить; доступность и «Нет соединения» в рабочие часы (ADR-014) пока не на чем считать | T-37: хранение рабочих часов и реализация `PATCH /api/schools/{id}` для них |
| Аналитика (`GET /api/analytics`) отдаёт долю замеров ниже договора, а агрегаты `m_hourly` / `m_daily` по plan.md §5 её не содержат и Wi‑Fi не исключают (T-03) | T-27 не сможет прочитать долю ниже договора и средние без Wi‑Fi только из агрегатов | T-19: добавить в агрегаты число замеров ниже договора и исключение Wi‑Fi (ADR-012) |
| Пресеты аналитики «неделя» и «месяц» в контракте — скользящие 7 и 30 суток по Asia/Almaty; ТЗ п. 5 («текущий день, неделю, месяц») можно читать как календарные (T-03) | цифры за «месяц» в панели и в ожиданиях заказчика могут не совпасть | T-27: подтвердить у лида; меняется только описание параметра `period` |
| В контракте есть поля и данные, которых нет в схеме БД plan.md §5: `providers.appeals_email` (T-34, T-48), хранилище выгрузок и их файлов (T-30, T-33), канал релиза агента у устройства (T-50) (T-03) | реализация эндпоинта упрётся в отсутствующую колонку или таблицу | задача реализации добавляет миграцию в том же слиянии; канал устройства — решает T-50 |
| Идемпотентность простоев есть только в контракте: `POST /api/outages` отвечает 409 `duplicate_outage` для того же устройства и `started_at`, но уникального индекса в `outages` нет (T-03) | пока приём простоев не реализован, ничего не ломается; реализация без индекса создаст дубль простоя при повторной досылке | T-16: уникальный индекс `(device_id, started_at)` миграцией и ответ 409 |
| Невалидная запись в `POST /api/measurements/batch` отклоняет весь запрос с 422 (индекс записи — в `errors[].field`), а ADR-006 удаляет запись из очереди только после 201/409 (T-03) | запись, которую сервер никогда не примет (например, после проверки диапазонов в T-51), останется в голове очереди до лимита 30 дней | решить в T-11/T-15 с лидом, удалять ли такие записи по `items[i]` и как их журналировать; решение — правкой ADR-006 |
| Версии FastAPI и Pydantic в `backend/pyproject.toml` не закреплены, а тест `test_openapi_file_matches_the_code` сравнивает `docs/reference/openapi.json` с кодом дословно (T-03) | новая версия FastAPI или Pydantic в CI может изменить текст схемы, и `make check-backend` покраснеет без изменений в коде | `make backend-install`, `make openapi`, закоммитить; закрепить версии — решение лида (правка `pyproject.toml`) |
| `errors[].message` по-русски только для частых типов ошибок Pydantic; для остальных остаётся английский текст Pydantic (T-03) | редкая ошибка валидации покажется в форме панели по-английски | дополнять `VALIDATION_MESSAGES` в `backend/app/core/errors.py`, когда такая ошибка встретится |
| Уникальность `measurement_uuid` в БД — только в паре с `measured_at` (`uq_measurements_measurement_uuid`): TimescaleDB не разрешает на hypertable уникальный индекс без колонки партиционирования (T-02) | повтор замера с теми же `measurement_uuid` и `measured_at` база отклоняет (ADR-006); тот же `measurement_uuid` с другим `measured_at` база не поймает — при штатной досылке такого нет, агент не меняет запись в очереди | T-15: при приёме искать дубль по одному `measurement_uuid` и отвечать 409 |
| MSI без подписи Authenticode, пока заказчик не даст сертификат | антивирус может ругаться на `VKO-Agent.msi` или блокировать установку | подпись — T-49; сертификат запросить у заказчика |
| SMTP заказчика не настроен | письма обращений и e-mail-уведомления об инцидентах не уходят; обращение сохраняется как «не отправлено», PDF сохраняется | параметры SMTP — от заказчика; отправка обращений — T-48, e-mail-уведомления — T-42 |
| Telegram-бот не заведён | Telegram-уведомления не уходят; остаются панель (SSE) и e-mail при настроенном SMTP | бота заводит команда в T-42 (нужен для демо-сценария 2, plan.md §15); токен — только в окружении |
| Ключ LLM не задан | AI-черновик обращения недоступен, текст пишется вручную | ключ — только в окружении, заводится в T-46 (нужен для демо-сценария 3, plan.md §15); черновик — T-47; Ollama — вариант для закрытого контура |
| Карта — публичные OSM-тайлы на демо | карта зависит от внешнего сервиса; без интернета подложка не грузится | свой tileserver — позже |
| Казахский язык интерфейса в MVP не планируется | панель только на русском | ADR-010; казахский — отдельной волной «позже» |
| VPN не реализуется | канал — HTTPS/TLS 1.2+ через Caddy и токен устройства | WireGuard — по требованию заказчика, отдельной задачей (ADR-010) |
| Готового Linux-пакета агента нет | на Linux агент ставится вручную через `vko-agent install` (T-06), без пакета | T-52, волна v1 |
| Самообновление агента в MVP не реализуется | новая версия агента ставится переустановкой MSI | T-50, волна v1 (п. 20, plan.md §4.6) |
| Аналитика инцидентов в MVP не строится | п. 19 закрыт частично: карточка, статусы и длительность есть (T-41), сводки по количеству, длительности и повторяемости по школам, районам и поставщикам нет | T-45, волна v1 (plan.md §7) |
| Выгрузки формируются синхронно | выгрузки больше 10 000 строк и PDF выполняются в запросе, а не в фоне; списка выгрузок нет | T-33, волна v1 (plan.md §12) |
| Резервное копирование БД не настроено | при потере тома `db` история замеров теряется | T-53 (pgBackRest), волна v1 (plan.md §13) |
| Sentry, Prometheus и Grafana не подключены | ошибки и нагрузка сервера видны только в логах контейнеров | T-54, волна v1 (plan.md §2) |
