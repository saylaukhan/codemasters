# Что нужно сделать на живой машине

Этот файл — список работ, которые нельзя было выполнить при разработке и которые остаются за
человеком. Не баги: всё перечисленное написано и выверено по коду, но ни разу не выполнялось на
работающем стенде — у разработки не было ни Docker, ни сервера, ни чистого Windows.

Читать сверху вниз: пункты идут в том порядке, в каком их имеет смысл выполнять, и следующий
обычно опирается на данные предыдущего. У каждого пункта — что запустить, что должно получиться
и куда записать результат.

Короткая сводка того же — в [README.md](README.md), раздел «Что ещё не проверено на живой
системе». Полный список недоделок — [docs/known-limitations.md](docs/known-limitations.md).

## Что понадобится

Docker, Go 1.23+, Python 3.12+, Node.js 24, git. Для пункта 7 — отдельная чистая машина с
Windows 10/11, для пункта 8 — Linux с systemd. Установка с нуля описана в
[docs/product/admin-guide.md](docs/product/admin-guide.md).

## Куда записывать результат

| Что получилось | Куда |
|---|---|
| Прогон прошёл | строка в [docs/worklog.md](docs/worklog.md): что запускали, что вышло, сколько заняло |
| Нашли дефект | задача в [docs/tasks/README.md](docs/tasks/README.md), ссылка на неё — в worklog |
| Решили оставить как есть | строка в [docs/known-limitations.md](docs/known-limitations.md) |
| Задача закрыта прогоном | статус `done (дата)` в [docs/tasks/README.md](docs/tasks/README.md) |

Правила слияния и оформления — [CONTRIBUTING.md](CONTRIBUTING.md).

## 1. Полный `make check`

Самое первое. Без Docker при разработке не запускались 259 тестов backend — те, что поднимают
PostgreSQL через testcontainers. Всё остальное (ruff, ruff format, mypy, 113 тестов backend,
весь agent, весь web) зелёное, и CI это подтверждает.

```bash
cp .env.example .env
make install
make check
```

Ожидается: зелёные `check-agent`, `check-backend`, `check-web`. Красный `check-backend` — почти
наверняка один из тестов с базой; смотреть на имя теста, а не на общее число.

В ветке T-59…T-61 (`docs/worklog.md`, 2026-09-22) весь набор — 400 тестов — прогнан на локальном
PostgreSQL 16 с PostGIS из apt и TimescaleDB, собранной из исходников, и зелёный; образ
`timescale/timescaledb-ha:pg16` из compose при этом не использовался, так что прогон на машине с
Docker остаётся нужным.

Отдельно стоит убедиться, что **перехэш токена устройства** отработал на настоящей базе:

```bash
cd backend && .venv/bin/pytest tests/test_agent_register.py -k upgraded -v
```

Токены устройств перешли с argon2 на sha256 (T-56). Старый хэш должен приниматься и переписываться
в новый формат при первой успешной проверке. 44 теста `test_security_tokens.py` проверяют это на
подменной сессии и SQL не исполняют — настоящий `UPDATE … RETURNING` проверяет только этот тест.

> Откат этого изменения ломает уже перехэшированные устройства: строку `sha256$…` старый код не
> примет, открытого токена на сервере нет. Откатывать — только вместе с восстановлением БД.

## 2. Развёртывание с нуля по инструкции администратора

Главный критерий T-57: администратор ставит систему без разработчика.

```bash
make up && make migrate && make seed
make api      # в отдельном терминале
make worker   # в отдельном терминале
make web      # в отдельном терминале
```

Дальше — строго по [docs/product/admin-guide.md](docs/product/admin-guide.md), не подглядывая в
код: вход под `admin@example.kz` (пароль `Password1`, только локально), справочники, пороги,
расписания, выдача кода установки агента.

Ожидается: инструкция проходится целиком и ни на одном шаге не приходится лезть в исходники.
Каждое место, где пришлось, — дефект инструкции, а не читателя.

Заодно соберите PDF с описанием API — он входит в состав поставки (plan.md §15):

```bash
make api-pdf   # docs/reference/api.pdf, около 68 страниц
```

## 3. Симулятор против живого сервера

При разработке гонялся только `--dry-run`. Нужен полный прогон и взгляд на панель.

```bash
make simulate n=1000 days=90
```

Ожидается: 350 школ, 1000 устройств, около 359 000 замеров, 4000 батчей. Симулятор на время
прогона поднимает настройку `agent_queue_retention_days` и **возвращает прежнее значение в
конце** — проверьте в админке, что после прогона там снова 30.

> Настройка глобальная, а не сессионная: пока идёт заливка, сервер принимает старые замеры и от
> настоящих агентов, а `kill -9` оставит её поднятой. Гоняйте симулятор на отдельной базе.

Затем откройте панель и убедитесь, что на этих данных:

- главная показывает KPI и карту ВКО, на карте есть школы всех четырёх статусов;
- карточка школы открывается, графики строятся;
- аналитика работает, в том числе тепловая карта час×день;
- есть хотя бы одна школа с устойчивым несоответствием договору;
- выгрузка XLSX содержит колонку «Кабинет» заполненной.

> Демо-данные «свежие» только `offline_after_s` (15 минут) после прогона: приём батча не двигает
> `last_seen_at`, его двигает только heartbeat. Дальше школы уйдут в «Нет соединения», а
> `make worker` заведёт около 350 ложных инцидентов. Показывать — сразу после прогона.

## 4. Нагрузочный тест и индексы (T-56)

Задача не закрыта: замеров нет, миграция с индексами не создана намеренно — любой индекс без
цифр был бы угадыванием.

Порядок и критерии — [docs/product/load-test.md](docs/product/load-test.md), §2. Кратко:

```bash
export VKO_LOAD_DATABASE_URL='postgresql+asyncpg://vko:vko@localhost:5432/vko_monitor'
cd backend && .venv/bin/pytest tests/test_load_endpoints.py -s
```

Меряются `GET /api/map/schools`, `GET /api/dashboard/summary`, `GET /api/analytics`,
`POST /api/measurements/batch` — p50/p95/max, плюс одновременный приём батчей от 1000 устройств.

Дальше по §5–§6 того же документа: подтвердить или отклонить каждого кандидата в индексы через
`EXPLAIN (ANALYZE, BUFFERS)`, добавить подтверждённые **новой** миграцией, перемерить, записать
таблицу «до/после» в [docs/worklog.md](docs/worklog.md). После этого T-56 переводится в `done`.

Первый прогон — это базовая линия. Смотреть надо на рост между прогонами, а не на абсолютные
величины: они зависят от машины.

## 5. Восстановление БД из бэкапа (T-53)

Бэкап, из которого ни разу не восстанавливались, — это не бэкап. Прогона не было ни одного.

```bash
docker compose -f docker-compose.yml -f docker-compose.backup.yml up -d
make backup
```

Затем полностью пройти раздел «Восстановление» в
[deploy/pgbackrest/README.md](deploy/pgbackrest/README.md): остановить пишущие сервисы, выбрать
момент по `pgbackrest info`, восстановиться на точку во времени, поднять базу, сверить
`max(measured_at)` и `alembic_version`, вернуть сервисы, снять новый полный бэкап.

Ожидается: база поднимается, данные на месте, в журнале PostgreSQL прошли строки восстановления
архива. Результат — в [docs/worklog.md](docs/worklog.md), этого прямо требует «Сделано, когда»
задачи T-53.

Не проверено ничем: поведение `stanza-create`, `archive_command` и `restore` на образе
`timescale/timescaledb-ha:pg16`.

## 6. Дашборд Grafana (T-54)

```bash
docker compose up -d
```

Открыть `http://127.0.0.1:3000` (наружу Grafana не публикуется — только с самого сервера), войти
под `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` из `.env`, открыть дашборд «Сервер мониторинга
ВКО».

Ожидается: все семь панелей рисуют данные, имена метрик `vko_*` совпадают с тем, что отдаёт
`GET /metrics`. Панели не должны быть пустыми после того, как через API прошло хоть сколько-то
запросов.

> API работает в одном процессе uvicorn: воркеры пока включать нельзя, они ломают метрики.
> Подробности — строка в [docs/known-limitations.md](docs/known-limitations.md).

## 7. Установка агента на чистый Windows

```
msiexec /i VKO-Agent.msi /qn ENROLL_CODE=VKO-0011-7F3K9-2QD4X SERVER_URL=https://<адрес>
```

Полностью — [docs/product/agent-install.md](docs/product/agent-install.md). После перезагрузки
служба должна подняться сама, зарегистрироваться по коду и в течение первого слота прислать замер,
видимый на карте.

Проверить `vko-agent status`: служба работает, устройство зарегистрировано, очередь пуста.

> MSI не подписан — сертификата Authenticode от заказчика пока нет. Windows покажет
> предупреждение SmartScreen; это ожидаемо, строка в `docs/known-limitations.md`.

## 8. Установка агента на Linux

```bash
sudo dpkg -i vko-agent_*.deb      # либо rpm -i vko-agent-*.rpm
systemctl status vko-agent
```

Ожидается: служба стартует при загрузке, работает от пользователя `vko-agent`, конфигурация в
`/etc/vko-agent/agent.yaml`, данные в `/var/lib/vko-agent`, токен в файле с правами 600.
Удаление пакета убирает unit и оставляет данные.

В CI проверяется только `.deb` на ubuntu-latest и только amd64; `.rpm` и arm64 не ставились
ни разу.

## 9. Контрольный прогон демонстрации (T-58)

Последний пункт: он опирается на всё предыдущее. Задача не закрыта, лист прогона пуст.

Пройти руками все семь сценариев из [docs/product/demo-scenario.md](docs/product/demo-scenario.md)
на `developing`, **без правок кода по ходу**. Заполнить лист контрольного прогона в конце того же
документа, найденные дефекты завести задачами в [docs/tasks/README.md](docs/tasks/README.md),
отчёт — в [docs/worklog.md](docs/worklog.md).

Понадобится заранее: данные из пункта 3, чистый Windows из пункта 7, ключ LLM для AI-черновика
обращения, SMTP и токен Telegram. Без них соответствующие шаги идут по запасному пути — он в
сценарии описан.

После успешного прогона лид сливает `developing` в `main` (ADR-001). Это и есть условие поставки.
