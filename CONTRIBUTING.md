# Как мы работаем с этим репозиторием

Это единственная инструкция по процессу. Если что-то здесь непонятно — спросите лида, и ответ
попадёт сюда же. Если что-то здесь противоречит реальности — исправьте в ветке `docs/…` по
этому же процессу.

Коротко: **своя ветка от `developing` → чек-лист `docs/checklist.md` → слияние в `developing`
→ запись в `docs/worklog.md`**. Pull Request'ов в проекте нет (ADR-001): гейт перед слиянием —
чек-лист, отчёт — журнал работ, ревью кода — по желанию. `main` обновляет только лид, слиянием
из `developing`, перед демо и поставкой.

Что где лежит: ТЗ — `docs/product/tz.md` (ссылки вида «п. 11»), план — `docs/product/plan.md`
(§1–§16), решения — `docs/architecture/decisions/` (ADR-001…014), задачи —
`docs/tasks/README.md` (T-01…T-58), интерфейс — `DESIGN.md`, правила для ИИ-агентов —
`AGENTS.md`.

Кода в репозитории пока нет: каркас, `Makefile` и `docker-compose.yml` появятся в T-01. Всё,
что ниже говорит о командах и путях, — целевое описание; до T-01 пункты чек-листа выполняются
вручную (ADR-001).

## 1. Настройка за 15 минут

Нужны: Go 1.23+, Python 3.12+ (uv или venv), Node.js 24, Docker Desktop, git, доступ к
репозиторию `saylaukhan/codemasters`.

```bash
git clone git@github.com:saylaukhan/codemasters.git
cd codemasters
cp .env.example .env     # локальные значения уже внутри, секретов там нет
make up                  # docker compose up -d db redis speedtest ndt7
make migrate             # alembic upgrade head
make seed                # справочники, GeoJSON районов ВКО, тестовые школы, dev-пользователи
```

Дальше — в отдельных терминалах, по мере надобности:

```bash
make api          # FastAPI на http://localhost:8000, Swagger — /api/docs
make worker       # celery worker + beat
make web          # панель на http://localhost:5173
make agent-run    # агент без установки службы: go run ./cmd/vko-agent run --config ./agent/dev.yaml
```

`make down` останавливает контейнеры, данные остаются. Локально `make up` Caddy не поднимает —
панель и API открываются напрямую по своим портам.

Переменные окружения — только в `.env.example` (появится в T-01), без значений: подключение
к БД и Redis, секрет JWT панели, ключ LLM для AI-черновиков обращений (T-46, ADR-011; без
него черновик недоступен, сервис не падает), токен Telegram (T-42), SMTP для уведомлений и
писем обращений (T-42, T-48; без него обращение помечается «не отправлено», PDF сохраняется —
ADR-011). Имена переменных фиксирует T-01. Начальное значение адреса сервера замеров —
переменная в `.env.example`, из неё `make seed` кладёт его в `settings` (T-05); в агент и
панель адрес не зашивается, рабочее значение меняется в админке (T-37) и уходит агенту через
`GET /api/agent/config` (T-17, T-13; п. 11, п. 20).

Порты: api 8000, web 5173, db 5432, redis 6379, speedtest 8080, ndt7 8081, caddy 80/443.

Dev-пользователи после `make seed` (пароль у всех `Password1`, только локально):

| Логин | Роль |
|---|---|
| `admin@example.kz` | Администратор |
| `oblast@example.kz` | Область |
| `rayon@example.kz` | Район/город (Усть-Каменогорск) |
| `school@example.kz` | Школа |
| `provider@example.kz` | Провайдер |

Проверить, что всё работает: `make check` — должен быть зелёным до того, как вы что-то
меняли. Красный на чистом `developing` — не ваша задача чинить внутри ветки фичи: скажите
лиду, это отдельная ветка `fix/…`.

## 2. Правило №1 — `main` защищён

- В `main` попадает только слияние из `developing`, только руками лида, только перед демо или
  поставкой (ADR-001). `main` всегда собирается и готов к поставке.
- `developing` — интеграционная ветка: всегда собирается, в неё сливаются задачи после
  чек-листа. Это то, что показываем на ближайшем демо.
- Никто не пушит в `main` напрямую — ни человек, ни агент.
- Force-push в общие ветки (`main`, `developing`) запрещён. Для Claude Code запрет закреплён
  технически в `.claude/settings.json` (§10.1).
- Случайно закоммитили в локальный `main`? Не пушьте:

```bash
git checkout -b feature/t-NN-what    # коммит уезжает в новую ветку
git branch -f main origin/main       # локальный main снова равен серверному
```

Общий путь у всех один: берёте задачу из `docs/tasks/README.md`, ставите ей `in-progress`,
работаете в своей ветке, проходите `docs/checklist.md`, ставите задаче `done (дата)`, сами
сливаете в `developing`, пишете `docs/worklog.md`.

| Роль | Что делает |
|---|---|
| Агент (Go) | служба, регистрация, планировщик, замеры, очередь, MSI, обновление — разделы B и I задач |
| Backend (Python) | API, схема БД, статусы, инциденты, экспорт, AI — разделы C, E, G, H |
| Frontend (React) | карта, сводка, карточки, аналитика, админка — разделы D, F, по `DESIGN.md` |
| Fullstack/DevOps | каркас, CI, Docker, RLS и безопасность, симулятор, документация поставки — разделы A, I, J |
| Лид | делит задачи и ставит даты в `docs/tasks/README.md`, принимает `docs/worklog.md`, единственный обновляет `main`, единственный переписывает историю (§9) |

Границы ролей — ориентир из plan.md §14, а не запрет: задача берётся тем, кто свободен.

## 3. Ветки

Одна задача — одна ветка. Имя латиницей, через дефис, с префиксом и номером задачи:

| Префикс | Для чего | Пример |
|---|---|---|
| `feature/` | новая функциональность | `feature/t-08-scheduler-slots` |
| `fix/` | исправление ошибки | `fix/t-15-batch-duplicates` |
| `db/` | миграция схемы | `db/t-19-continuous-aggregates` |
| `docs/` | только документация | `docs/t-57-admin-guide` |
| `chore/` | инфраструктура, CI, зависимости | `chore/t-01-ci-workflow` |

```bash
git checkout developing && git pull
git checkout -b feature/t-08-scheduler-slots
```

Ветка живёт не дольше недели. Если задача больше — режьте задачу, а не растите ветку: размер L
в `docs/tasks/README.md` означает, что первое слияние — каркас.

Держите ветку свежей: `git fetch origin && git rebase origin/developing`. Если ветка уже
запушена и переписывать её не хочется — `git merge origin/developing`. Главное, чтобы конфликты
решались у вас до слияния, а не в `developing` после.

## 4. Коммиты

Conventional Commits, на английском, в повелительном наклонении, до 72 символов в заголовке.
Тип — `feat`, `fix`, `db`, `docs`, `chore`, `refactor`, `test`; область в скобках — когда
изменение относится к одному компоненту: `agent`, `api`, `web`; для `db`, `docs` и `chore`,
затрагивающих репозиторий целиком, область не ставится.

```text
feat(agent): add slot scheduler with jitter
feat(api): accept measurement batches and dedupe by uuid
feat(web): add school list with status badges
fix(agent): keep queue entry until server returns 201 or 409
db: add measurements hypertable and fk indexes
refactor(api): move threshold lookup into status service
test(api): cover foreign scope on schools list
chore: run make check in ci on push to developing
```

Один коммит — одна мысль. «Final changes», «fix», «wip» — не заголовки. Если хочется написать
«и ещё поправил…» — это второй коммит.

Без подписи ИИ: никаких `Co-Authored-By`, упоминаний ассистента в сообщении коммита. Автор
коммита — человек, который работает.

## 5. Перед слиянием

```bash
make check          # check-agent + check-backend + check-web — всё зелёное
```

Если трогали `backend/alembic/versions/`:

```bash
make db-reset       # drop + create + migrate + seed — миграции применяются с нуля
make check-backend  # ruff, mypy, pytest — старые и ваши новые тесты зелёные
```

Если трогали контракт API (схемы в `backend/app/schemas/`, роутеры в `backend/app/api/`):
`make openapi`, затем закоммитить `docs/reference/openapi.json` и `web/src/api/generated/*`
вместе с изменением (ADR-009).

Если трогали UI: откройте экран в светлой и тёмной теме и на ширине 1024px, пройдите
`DESIGN.md` §8; отметку «проверено в светлой и тёмной теме и на 1024px» — в запись
`docs/worklog.md`.

Дальше:

1. Пройдите `docs/checklist.md` целиком. Пустой чек-лист — не сливаем.
2. Подготовьте черновик записи для `docs/worklog.md` (§8) — пока не в ветке, он ляжет в
   `developing` после слияния — и поставьте задаче `done (дата)` в `docs/tasks/README.md`
   (это коммит в вашей ветке).
3. Ревью — по желанию: если сомневаетесь, покажите diff коллеге до слияния.
4. Слейте сами. Сразу после слияния, до `git push`, допишите в запись хэш merge-коммита и
   закоммитьте `docs/worklog.md` прямо в `developing` одним коммитом `docs: …` — это
   единственный прямой коммит в `developing`, делает его автор слияния (не агент):

```bash
git checkout developing && git pull
git merge --no-ff feature/t-08-scheduler-slots
make check                                    # developing собирается после слияния
git log -1 --format=%h                        # хэш merge-коммита — в строку «Сделано»
git add docs/worklog.md && git commit -m "docs: add worklog entry for T-08"
git push origin developing
git branch -d feature/t-08-scheduler-slots
git push origin --delete feature/t-08-scheduler-slots
```

Если `make check` после слияния красный — не пушьте. Незапушенное слияние откатывается
`git reset --merge ORIG_HEAD`; чините в своей ветке и сливайте заново. Чтобы такого не было,
подтяните `developing` в ветку заранее (§3) и прогоните `make check` там.

Ветка после слияния удаляется — локально и на сервере. Целевой размер слияния — до 400 строк
diff; больше — режьте.

## 6. Миграции

- Только вперёд (forward-only). Миграция, влитая в `developing`, не редактируется, не
  переименовывается и не удаляется. Ошиблись — новая миграция, которая исправляет.
  `alembic downgrade` не используем.
- Имя ревизии: `YYYYMMDD_HHMM_short_name`. Создаётся командой `make migration name=short_name`
  (`alembic revision --autogenerate`); автогенерацию читайте глазами — она не знает про RLS и
  hypertables.
- Каждая новая таблица обязана иметь: индексы на все FK; `created_at` / `updated_at`, где
  уместно; RLS-политику по `app.user_scope`, если у таблицы есть область видимости — школа,
  район, провайдер (ADR-008); hypertable TimescaleDB, если это временной ряд (ADR-003); тест в
  `backend/tests/`.
- Имена таблиц — snake_case, множественное число; время — `timestamptz` в UTC (ADR-014).
- Seed (`make seed`) — справочники, GeoJSON районов ВКО, тестовые школы, dev-пользователи и
  значения по умолчанию порогов, расписаний и рабочих часов (T-04; базовые пороги — T-17,
  расписания и рабочие часы — T-37). Тестовые школы и dev-пользователи — только локально;
  что из seed нужно в production — решает T-57 при описании развёртывания.
- Перед слиянием: `make db-reset` → `make check-backend` (§5).
- Конфликт ревизий (двое ответвились от одной ревизии — `alembic upgrade head` падает с
  «Multiple head revisions»): порядок задаёт цепочка `down_revision`, а не имя файла. После
  rebase поставьте в своей ревизии `down_revision` на последнюю влитую ревизию (при
  необходимости переименуйте файл на более позднее время, чтобы имена шли по порядку) и
  прогоните `make db-reset`. Влитую в `developing` ревизию не трогаем.

Как писать тест на права: для таблицы с областью видимости проверьте, что своя роль видит
строку, чужая — нет, и что `is_active = false` не удаляет историю (ADR-008). Первый такой тест
появится в T-20; до него образец — первый файл этого вида, который вы создадите.

- GUI и трей у агента — агент служба без окон, диагностика через CLI `status`.
- VPN по умолчанию — канал HTTPS/TLS через Caddy плюс токен устройства; WireGuard — только по

- Свой движок speedtest — LibreSpeed основной, ndt7 резервный (ADR-012).

- Персональные данные учеников и учителей — никогда; единственные ПД — `school_contacts`, и в
  LLM они не уходят (ADR-011).
- Мобильное приложение — панель проверяется на 1024px, этого достаточно.
- i18n-фреймворк на MVP — строки по-русски в компонентах, статусы из `labels.ts`.
- Свои UI-компоненты вместо Ant Design — только обёртки в `web/src/components/ui/`.

Кроме того, по соглашениям команды (`AGENTS.md` §2; `docs/checklist.md`):

- Зависимости без обсуждения — сначала посмотрите, что уже есть в `go.mod`, `pyproject.toml`,
  `package.json`.
- `any`, `@ts-ignore`, `type: ignore`, `print` и `console.log` в коде; секреты в коде и в
  документации.

Архитектурные решения и почему они такие — `docs/architecture/decisions/`. Если ваша задача
требует решения, которого там нет, — напишите ADR в той же ветке: это 20 строк, следующий
номер, статус «предложено» до слияния (см. `docs/architecture/decisions/README.md`).

## 8. Как отчитаться

Когда задача влита в `developing` или застряла — запись в `docs/worklog.md`. Три строки:
**Сделано**, **Не сделано**, **Потрачено / Застрял на**, плюс итог `docs/checklist.md` (что
пропущено и почему); для UI — отметка, что проверено в светлой и тёмной теме и на 1024px.
«Не сделано» — обязательная строка, даже если там «ничего». Запись коммитится прямо в
`developing` сразу после слияния, до `git push` (§5); запись «застрял» — тем же способом.

```text
### 2026-09-16 · T-08 · Агент: планировщик слотов с джиттером и догоняющий замер
Сделано: слоты из конфигурации, случайный момент внутри слота, догоняющий замер после старта
службы; тест с подменённым временем. Слияние: <хэш merge-коммита в developing>.
Чек-лист пройден полностью.
Не сделано: применение нового расписания без перезапуска службы — уйдёт в T-13 вместе с
конфигурацией с сервера; строка добавлена в docs/known-limitations.md.
Потрачено / Застрял на: ~1,5 дня. Застрял на генераторе случайного смещения в тесте — решено
подменой источника времени.
```

Три строки честности ценнее длинного отчёта. Недоделка без строки в
`docs/known-limitations.md` — это не недоделка, а сюрприз для коллеги. Черновик записи может
подготовить агент, пишете и подписываете её вы.

---

## 9. Если что-то пошло не так

- **Сломан `developing`** (красный `make check` после чьего-то слияния). Не откатывайте руками
  и не переписывайте историю: ветка `fix/…` с исправлением или `git revert` коммита слияния,
  затем обычный путь через чек-лист. Кто сломал — тот и чинит, остальные не ждут молча, а
  говорят.
- **Закоммичен секрет** (ключ, пароль, токен, содержимое `.env`). Немедленно сообщите лиду.
  Ключ ротируется в любом случае — даже если коммит ещё не запушен. Коммит переписывается —
  это единственный случай переписывания истории в общих ветках, и делает это лид.
- **Конфликт в сгенерированных файлах** (`web/src/api/generated/*`,
  `docs/reference/openapi.json`). Не решайте руками: после rebase выполните `make openapi` и
  закоммитьте результат.
- **Конфликт миграций** (две ревизии от одного родителя) — см. §6: поправить `down_revision`,
  затем `make db-reset`. Влитую в `developing` ревизию не трогаем.
- **Тесты упали после rebase**, хотя в ветке были зелёные. Это не повод их выключать:
  разберитесь, чьё изменение и какое поведение верное, при необходимости — новый тест на оба
  случая.

## 10. Работа с ИИ-ассистентом (Claude Code, Codex)

Каждый в команде работает со своим агентом на своей машине, в своей ветке. Агент — это быстрый
младший разработчик без памяти о вчерашнем дне: он сделает ровно то, что вы попросили, и ещё
что-нибудь, если вы не запретили. Правила для него — `AGENTS.md` (Claude Code читает его через
`CLAUDE.md`, Codex — напрямую). Правила для вас — ниже.

### 10.1 Что стоит в репозитории и зачем

| Файл | Кто читает | Что делает |
|---|---|---|
| `AGENTS.md` | Claude Code, Codex, любой агент | Правила: что никогда, что всегда, карта проекта, инварианты ТЗ (§8), шаблоны |
| `CLAUDE.md` | Claude Code | Одна строка `@AGENTS.md`, чтобы правила были в одном месте |
| `.claude/settings.json` | Claude Code | **Технический запрет** опасных команд, см. группы ниже. Плюс отключена подпись ИИ в коммитах (`includeCoAuthoredBy: false`) |
| `CLAUDE.local.md` | только ваш Claude Code | Ваши личные инструкции (§10.3). В `.gitignore`, в репозиторий не попадает |
| `.claude/settings.local.json` | только ваш Claude Code | Ваши личные разрешения. Тоже в `.gitignore` |

Что запрещено в `.claude/settings.json` (deny — команда не выполнится):

| Группа | Что именно |
|---|---|
| Общие ветки и история | push в `main`, force-push; `reset --hard`, `git clean`, `branch -D`, `filter-branch`, `rebase -i`, `config --global` |
| Файловая система | `rm -rf`, `sudo` |
| Docker-данные | `docker compose down -v`, `docker volume rm`, `docker system prune` |
| Миграции назад | `alembic downgrade`, `alembic stamp` |
| Деплой и подпись — только руками | `ssh`, `scp`, `docker push`, `signtool`, `msiexec` |
| Секреты | чтение и правка `.env*`, кроме `.env.example` |
| Сгенерированное | правка `web/src/api/generated/*` и `docs/reference/openapi.json` |

Что требует подтверждения (ask — агент остановится и спросит): `git push`, `git merge`,
`git commit --amend`; установка зависимостей (`go get`, `pip`/`uv add`, `npm install`); правка
`AGENTS.md`, `CONTRIBUTING.md`, `.claude/settings.json`, `docker-compose.yml`, `deploy/*`,
`Makefile`, `go.mod`, `pyproject.toml`, `package.json`, `.github/*`, `alembic/versions/*`
(новые миграции — можно, но с подтверждением).

Codex не читает `.claude/settings.json` — для него запреты существуют только текстом в
`AGENTS.md`. Поэтому Codex запускайте в режиме с подтверждением команд, не в полностью
автономном режиме без песочницы.

### 10.2 Правила для человека

1. **Задачу ставите вы, не агент.** Первое сообщение — номер задачи и границы:
   > `T-08 · планировщик слотов. Только agent/internal/scheduler/ и его тест. Конфигурацию с
   > сервера не трогать — это T-13. Перед коммитом покажи вывод make check.`
2. **Читайте diff целиком** перед коммитом и перед слиянием. Не понимаете строку — спросите
   агента «зачем это», и если ответ неубедителен — уберите. За слияние отвечаете вы, не агент.
3. **Одна сессия — одна задача.** Закончили — новая сессия, чистая ветка. Агент, который
   «заодно» переписал соседний файл, — это конфликт для коллеги.
4. **Не давайте агенту `main` и `developing`.** Он работает в вашей ветке; слияние делаете вы
   после чек-листа. Предложение «слить в developing для скорости» — ошибка агента, не опция.
5. **Проверки запускаете сами**, даже если агент сказал, что они зелёные: `make check`, для
   миграций — `make db-reset`, для контракта — `make openapi`.
6. **Секреты агенту не показывайте** и не просите «прочитать `.env`». Всё, что ему нужно, есть
   в `.env.example`. Claude Code чтение `.env*` заблокировано; Codex — нет.
7. **Не просите агента «починить тесты»,** если тесты падают из-за вашего изменения. Просите
   объяснить, почему они падают. Выключенный или ослабленный тест — скрытый баг в `developing`.
8. **Не давайте агенту править** применённые миграции, сгенерированные файлы
   (`web/src/api/generated/*`, `docs/reference/openapi.json`), зависимости (`go.mod`,
   `pyproject.toml`, `package.json`) без обсуждения, чужие ветки. Claude Code это заблокирует
   или спросит сам; Codex — нет.
9. **Записывайте решения, а не переписки.** Если в ходе сессии вы приняли решение, которого нет
   в `docs/architecture/decisions/`, — 20 строк ADR в той же ветке.
10. **Запись в `docs/worklog.md` пишете вы** (§8), агент может подготовить черновик.

### 10.3 Личные инструкции агенту

`CLAUDE.local.md` в репозиторий не попадает (он в `.gitignore`), поэтому после clone создайте
его в корне сами — четыре строки по этому шаблону:

```text
Кто я: <роль: агент (Go) / backend (Python) / frontend (React) / fullstack/DevOps>
Сейчас работаю над: T-__ · <название из docs/tasks/README.md>
Разрешено без вопросов: <…>
Только с подтверждением: <…>
```

Общие правила `AGENTS.md` там повторять не нужно — они действуют всегда. Никогда не коммитьте
этот файл и не пересылайте его с ключами внутри.

### 10.4 Стартовый шаблон сессии

```text
Задача: T-__ · <название> (docs/tasks/README.md)
Границы: <что трогаем / что не трогаем>
Ветка: feature/t-__-<что>
Перед началом: git status чистый, developing подтянут.
Перед коммитом: покажи вывод make check (и make db-reset, если миграция).
Коммит: Conventional Commits с областью, без подписи ИИ. Пуш только в мою ветку.
Слияние в developing делаю я после docs/checklist.md.
В конце: черновик записи для docs/worklog.md (сделано / не сделано / застрял на).
```
