# Симулятор агентов

Генератор нагрузки и истории для демо и нагрузочных тестов: 350 школ, 1000 ПК, история замеров
(plan.md §15, сценарий 7). Ходит в сервер через тот же API, что и настоящий агент (ADR-006):
регистрирует устройства (`POST /api/devices/register`), шлёт замеры пачками
(`POST /api/measurements/batch`), простои (`POST /api/outages`) и heartbeat. Школы берёт из seed
(T-04), пороги и расписание — из `GET /api/agent/config`, договорные скорости — из
`GET /api/schools/{id}/lines`: в симуляторе не зашито ни одного порога и ни одного кода школы
(ТЗ п. 11, п. 20). Прямой записи в БД нет: что сервер не принимает от агента, того не может
записать и симулятор.

Только стандартная библиотека Python — ни одной зависимости из `backend/pyproject.toml`.

```bash
make simulate n=1000 days=90                  # n — количество ПК, days — глубина истории
SIM_ADMIN_PASSWORD='…' make simulate n=1000 days=90
python3 simulator/simulate.py --schools 350 --devices 1000 --days 90 --dry-run
```

`make simulate` запускает `simulate.py` интерпретатором из `backend/.venv`, но симулятор
работает и любым `python3` 3.12+.

## Аргументы

| Аргумент | По умолчанию | Зачем |
|---|---|---|
| `--schools` | 350 | сколько школ из seed занять; остальные останутся «Нет данных» |
| `--devices` | 1000 | сколько ПК раскидать по школам по кругу (каждой школе — минимум один) |
| `--days` | 90 | глубина истории; сервер примет не больше 30 суток (см. «Ограничения») |
| `--api` | `http://localhost:8000` или `API_BASE_URL` | адрес сервера |
| `--admin-email` | `admin@example.kz`, `SIM_ADMIN_EMAIL` | под кем выдавать коды: право `devices:manage` есть только у «Администратора» |
| `--admin-password` | `SIM_ADMIN_PASSWORD` | пароль администратора; в коде не хранится (AGENTS.md §7) |
| `--state` | `simulator/data/state.json` | файл с `device_id` и токенами зарегистрированных ПК |
| `--workers` | 8 | сколько ПК шлют замеры параллельно |
| `--register-rate` | 20 | регистраций в минуту; как `AGENT_REGISTER_RATE_LIMIT` сервера |
| `--dry-run` | — | только план и примеры замеров, без обращений к серверу |

## Профили

Профиль выдаётся школе по фиксированному циклу, поэтому в данных всегда есть школы всех
статусов ТЗ п. 13 — даже на прогоне из шести школ. Все профили — чистые функции от устройства и
момента: без сети, без БД, без `random`.

| Профиль | Что показывает | Статус школы |
|---|---|---|
| норма | всё в пределах порогов, скорость не ниже договора | Норма |
| деградация по часам | утром норма, с уроками растёт ping, днём — и потери | Нестабильно / Критично |
| нестабильно | один показатель за порогом, отклонение меньше допустимого | Нестабильно |
| критично | два показателя за порогом одновременно | Критично |
| простой | `connection_status: offline` плюс период в `POST /api/outages` | Нет соединения |
| ниже договора | пороги соблюдены, скорость ниже договорной (T-29) | Норма + несоответствие |

Часть ПК (со второго в школе) отдаёт замеры по Wi-Fi — `iface_type: wifi`. Такие замеры сервер
не учитывает ни в статусе школы, ни в сравнении с договором (ADR-012), и в данных они нужны
именно поэтому. Но статус самому замеру сервер всё равно ставит — он виден в карточке ПК,
в `GET /api/devices/{id}/measurements` и в выгрузке, — поэтому по воздуху цифры хуже, чем по
кабелю, но остаются с той же стороны порогов: Wi-Fi-ПК школы «норма» не покажет «Критично».

Школе с договором близким к порогам профиль «ниже договора» не достаётся: она не может
одновременно быть «Норма» и не дотягивать до договора. Такая школа меняется профилем с первой
подходящей — перестановка детерминированная.

## Повторный запуск

`measurement_uuid` — `uuid5` от `device_uid` и момента слота, момент внутри слота тоже
детерминированный. Поэтому повторный запуск шлёт те же записи, а сервер отвечает 409
`duplicate_measurement` и ничего не дублирует (ADR-006). Так же ведут себя простои: ключ
идемпотентности — устройство и `started_at`.

Регистрация повторно не выполняется: `device_id` и токен лежат в `--state`. Файл — вне git
(правило `data/` в `.gitignore`) и создаётся с правами `600`, потому что в нём токены устройств.
Если файл потерять, ПК зарегистрируются заново по тому же `device_uid`: дублей устройств не
будет (`device_uid` уникален), но уйдёт ещё столько же кодов установки. Файл помнит адрес
сервера: запуск того же состояния против другого `--api` останавливается сразу, а не падает
позже на чужих токенах.

**Перед демо прогон повторяют.** Повторный запуск быстрый (регистрация пропускается, замеры
приходят как 409) и заново освежает heartbeat — без этого статусы живут 15 минут, см.
«Ограничения».

## Ограничения

- **Глубина истории — 30 суток, а не 90.** Сервер не принимает замер старше очереди агента
  (`MAX_QUEUE_AGE`, 31 сутки, ADR-006): всё, что старше, отклоняется с 422. `--days 90`
  принимается, но симулятор предупреждает об обрезке до первого запроса к серверу, а не в конце
  прогона. Требование T-55 «3 месяца истории» и контракт сервера противоречат друг другу:
  заполнить 90 суток можно только прямой записью в БД мимо API — это решение лида (пункт
  «Сделано, когда» T-55 и строка в `docs/known-limitations.md`). От этого же зависит T-56:
  нагрузочный тест получит объём за 30 суток, а не за 90.
- **Скорость регистрации.** Сервер считает коды установки на адрес
  (`AGENT_REGISTER_RATE_LIMIT`, по умолчанию 20 в минуту), поэтому 1000 ПК регистрируются около
  часа. Подняли лимит в `.env` — поднимите и `--register-rate`.
- **Инциденты и флаг несоответствия договору** проставляет Celery: `detect_line_task` после
  батча и `contracts.recompute_compliance` раз в 15 минут (T-40, T-29). Без `make worker` замеры
  придут, а инцидентов и `lines.compliance_*` не будет.
- **Исторический heartbeat невозможен:** сервер пишет момент по своим часам, поэтому доступность
  в прошлом симулятор не воспроизводит.
- **Данные «живут» 15 минут после прогона.** `last_seen_at` двигает только обработчик heartbeat,
  приём батча — нет, а heartbeat симулятор шлёт один раз в конце. Через `offline_after_s`
  (по умолчанию 900 с, админка) все школы читаются как «Нет соединения» в рабочие часы и «Нет
  данных» вне их, что бы ни было намерено; с `make worker` `incidents.detect_all` за те же
  15 минут откроет инцидент «Нет соединения» на каждой линии. Лечится повторным прогоном перед
  демо или увеличением `offline_after_s` в админке на время показа.
- **Кабинет точки мониторинга проставляет симулятор.** Seed (T-04) создаёт точку без кабинета, а
  агент кабинет не создаёт — `POST /api/devices/register` только выбирает по нему точку
  (ADR-005). Поэтому симулятор перед регистрацией пишет кабинет главной точке школы через
  `PATCH /api/schools/{id}/points/{point_id}`; без этого колонка «Кабинет» в выгрузке пустая
  (ТЗ п. 9). Кабинет, проставленный человеком, не трогается.
- **Одно зашитое пороговое правило.** «Нестабильно» строится как превышение порога на 8–20 %:
  `GET /api/agent/config` отдаёт `ThresholdValues` без `unstable_deviation_pct`, и узнать
  допустимое отклонение симулятор не может. При отклонении меньше 8 %, выставленном в админке
  (ТЗ п. 11), профиль «нестабильно» начнёт давать «Критично». Остальные пороги — только с сервера.
- **Тест не входит в `make check`:** `make check-backend` ходит только в `backend/`. Запускать
  руками: `backend/.venv/bin/python -m pytest simulator/`.

## Тест

`simulator/test_simulate.py` — генератор профилей: каждый профиль даёт ожидаемый статус (и по
кабелю, и по Wi-Fi), метрики лежат в допустимых диапазонах T-51, `measurement_uuid`
повторяется, Wi-Fi помечен и медленнее, «ниже договора» держится в порогах. Ни сети, ни
импорта backend: статус считает `simulate.expected_quality` — копия правила ADR-004, которая же
печатается в `--dry-run`.
